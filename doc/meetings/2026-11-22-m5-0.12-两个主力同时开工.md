## 1. @stage 依赖（T1）

**格式**：`depends_on` 每项匹配 `^([\w-]+)(?:@([\w-]+))?$`。`Tn` 表示上游任务 done（不变）；`Tn@<stage_id>` 表示上游这个阶段已有交接。新建一个小模块 `src/engine/deps.ts`，导出 `parseDep(d) → { key, stage: string | null }` 和 `depSatisfied(...)`，供 scheduler、validatePlan 和 T3 的预览共用，不要在三处各写一遍正则。`depends_on` 在库里仍然是原样字符串数组，所以 0.11 的数据库不需要迁移。

**满足条件**：
- 上游任务已 done，任何 `@x` 都算满足；
- 否则取上游该阶段**最近一次**尝试：状态为 done、awaiting_approval 或 approved，并且有 handoff；
- 修正一点：如果 x 是审查阶段（`on_reject` 有值），还要求那份交接的 `verdict = approve`。审查打回的交接不能放行下游；
- 上游正在返工（该阶段最近一次尝试是 ready 或 in_progress）时，还没开工的下游继续等。已经开工的不撤销。

**validatePlan 拒绝条件**（逐条报，每条写明原因）：
1. 格式不对：`T1@`、`@impl`、`T1@a@b`；
2. 上游不在清单里（沿用现有报错）；
3. 阶段不存在：按 `templateStages(owner, reviewer)` 推出上游实际会有的阶段。上游没有审查人却写 `@review` 时报「T1 没有审查人，没有 review 阶段」，并列出可选的阶段；
4. 同一个上游同时写了 `T1` 和 `T1@x`：报重复依赖；
5. 成环：`Tn@x` 当作对 `Tn` 的依赖，保守处理；
6. 带阶段依赖的两个任务（下游和上游）任何一方 `paths` 为空：拒绝。原因是两者会并行，没有范围就无法按租约分开提交；
7. 两者的 `paths` 在 `globsOverlap` 下重叠：拒绝，并列出重叠的 glob。原因是上游的租约要到任务结束才释放，重叠时下游只会干等，@stage 就失去了意义。

**调度**：`schedule` 目前只在 advance 时调用（任务完成、或批准后进下一阶段），需要在每次 handoff 落库后、以及 decide(approve) 后都调用一次 `schedule(run)`。

**based_on**：下游开工时，`task.dependencies[]` 中带 @ 的每项加上 `based_on: { stage, handoff_id, commit }`，取当时满足条件的那份交接；不带 @ 的项不加。下游每次交接都把 `based_on`（数组：`{ dep, stage, handoff_id, commit }`）写进 `HandoffData`。依据取开工时那次，记在 task 行上（`tasks.dep_basis` JSON 列，旧库补列为 null），不按交接时重新计算。

**上游变化通知信**（写死格式）：
- 触发：上游 U 的 s 阶段有新交接落库，且某个已开工（active）的下游 D 有 `U@s` 依赖、`based_on.handoff_id` 不是这份。上游任务被取消：目前只有 stopRun 会取消任务，而它会把下游一起取消，所以这一版实际上不会触发，代码里留同一个入口即可；
- 收件人：D 当前 in_progress 那次尝试的成员（实现中就是负责人，审查中就是审查人）。D 的尝试如果还是 ready、信没取，就不另发通知，因为取信时 payload 会带上变化；
- 信：kind `system`，from `bridge`，`ack_required: false`，id `upstream-<run>-<D.key>-<handoff_id>`（去重）；
- 主题：`上游变化：T1 的 implement 有新交接`；
- 正文（固定几行）：
  ```
  上游：T1「标题」 阶段 implement（codex）
  新交接：<commit 短号>，摘要：<summary>
  改动文件：a、b、c
  你开工时依据的是：<旧 commit 短号>
  改动是否影响你，自己判断；需要跟进就改，不需要就继续。本任务不会被打断或作废。
  ```
- 下游的任务 payload（包括审查信）增加 `upstream_changes: [{ dep: "T1@implement", based_on_commit, latest_commit, latest_summary, files_changed }]`，只列 based_on 不是最新那份的项，没有变化时不出现这个字段。审查信的 instructions 加一句：「upstream_changes 列出下游开工后上游又改过的交接，审查时确认本任务和最新上游兼容。」

## 2. 审查优先投递（T1）

`deliver` 把 ready 的尝试排序：`stageOf(task, a.stage_id).on_reject` 有值的排在前面，同类按 id（即创建时间）。已经发出的任务信（queued、rung 或 fetched）不换成别的，进行中的也不抢占。实现很小，和 T1 放在一起合适。

## 3. 长命令心跳（T2，我来做）

- `report_progress(agent_id, text, busy_minutes?)`，`busy_minutes` 用 zod 限制为 `int().min(1).max(60)`，越界由 schema 直接拒绝并报范围，不悄悄截断；
- 在 presence 里记 `busyUntil`（内存）。**清除规则**：submit_handoff、submit_meeting_turn、leave、release、身份被接管时清除；下一次 report_progress 带 busy_minutes 时覆盖，不带时清除；daemon 重启后自然丢失；
- sweep：成员的 fetched、需要确认、且对应尝试 in_progress 的任务信，在 `now < busyUntil` 时不报 ack_overdue。过了 busyUntil，照现有规则看 lastSeenAt，相当于两者取较晚的那个；
- 我倾向把会议信也纳入豁免（读代码写提案也可能超过 10 分钟）。会议若不同意，就只豁免任务信；
- `agents[].activity` 增加 `busy_until`（ISO 时间）。Office 和成员详情显示「执行长命令，预计 HH:MM 前」（本地时间）。过期后不再显示；
- `report_progress` 的工具描述和 join 守则（presence.ts 的 protocol 第 2 条）都加：「预计超过 5 分钟不调用桥工具时（比如跑完整 smoke），先 report_progress 并带上 busy_minutes」。

## 4. 定稿预览（T3）

`src/engine/plan-preview.ts`，纯函数 `previewPlan(tasks, stagesFor)`，其中 `stagesFor(task)` 由调用方传入 `templateStages`，这样模块不依赖 config。

**模拟**：离散时间，每个阶段 1 个单位，每个成员同时只做一个阶段，挑选时审查优先，和 deliver 一致。阶段级依赖按 `parseDep` 处理，审批门不计时。paths 重叠的两个任务不能同时进行，用来模拟租约；`globsOverlap` 是纯函数，可以复用。

**输出**：
```
{ waves: [{ n, items: [{ agent, task, stage, kind: "work"|"review" }] }],
  members: [{ agent, work: n, review: n }],
  total_units, hints: [{ code, text }] }
```

**提示规则**（写死，只提示，不拦截）：
- `single_coder`：所有非审查阶段都属于同一个成员，另一位参与者只有审查阶段。文案：「只有 codex 在写代码，claude 只负责审查」；
- `serial_chain`：任务数 ≥ 2 且每一波都只有 1 项。文案：「整个计划是一条串行链，共 N 步」；
- `owner_queue`：同一负责人名下有两个任务，它们之间没有依赖路径（双向都不可达），却被排进了不同的波次。文案：「codex 名下的 T1、T3 之间没有依赖，但只能先后做」；
- `path_serialized`：两个没有依赖关系、负责人不同的任务因为 paths 重叠只能串行。文案：「T2 和 T3 没有依赖，但 paths 重叠（src/mcp.ts），只能先后进行」。

**接入**：定稿轮 `submit_meeting_turn` 的返回里加 `preview`。面板的定稿卡从最后一份定稿的 tasks 现场计算，不落库，不改表。`guide.final` 和 `taskSpec` 补两句：`Tn@stage` 的写法和限制；「主力成员尽量同时各做一个实现任务，并交叉审查」。`mcp.ts` 里 `planned.depends_on` 的描述同步更新。

### 阶段依赖与审查投递

- `depends_on` 接受 `<任务ID>` 或 `<任务ID>@<阶段ID>`，两段均沿用现有 ID 字符集，大小写精确匹配。拒绝空段、多余的 @、未知任务、自依赖、未知或被模板裁掉的阶段、成环，以及阶段依赖上下游的 `paths` 按现有 `globsOverlap` 判定重叠。成环按任务投影检查，`T1@review` 在 T1 无审查人且模板裁掉 review 时直接报错。保留旧格式及其完成条件。
- 阶段依赖取该阶段最新一次 attempt，必须实际已有交接且状态为 `done`、`awaiting_approval` 或 `approved`。交接落库、attempt 状态更新后立即重调度，覆盖有审批门和直接推进两条路径。下游拿到租约、从 pending 转 active 时固定交接 ID，任务信的对应 `dependencies[].based_on = { stage, commit }` 以及该任务的交接都引用这份快照。旧库缺字段照常读，未产生 Git 提交时 commit 为 null。文件夹里的等待原因复用同一依赖判断。
- 对已经启动的直接下游，上游同一阶段出现新交接，或上游被单独取消时，给下游负责人发 `kind: system`、`ack_required: false` 的系统信。主题为「上游变更：T1@implement → T2」或「上游取消：T1@implement → T2」。正文固定包含运行、上游任务和阶段、下游任务、原提交、新提交或「无」、交接摘要或取消原因，末句为「请判断改动是否影响你的任务。需要跟进就修改，否则继续。」按运行、下游任务、依赖、交接 ID 或取消事件去重。下游审查信以结构化 `upstream_changes` 列出同一份变化记录，即使负责人已读信也保留。只打回审查、还没出现新交接时，下游保持原基线继续。
- 现有面板只支持停止整个运行。建议 T1 加单任务取消的调度入口，T3 在现有任务卡加入口，复用确认控件。取消上游时继续保留已启动的直接下游，递归取消因此无法开工的 pending 后继，避免运行永久挂起。保留 ACP 取消期租约。整轮停止时上下游一起结束。
- `deliver` 从尚未投递的 ready 阶段优先选 `on_reject` 有值的审查，同类按 attempt ID 从小到大。已发信和手上在做的阶段继续。批量就绪时先收集候选再投递。两份独立交接可能同时执行 Git 命令，建议把桥内「选定范围、提交、读 SHA」串行化。并发 smoke 要核对两份交接的 SHA 和各自的文件，避免索引锁让交接在提交失败后仍推进，或两份交接记到同一个 SHA。

## 先回应用户的三个问题

### ① 上游审查打回后，已开工的下游只收通知、不作废，够不够？

不作废是对的。多数返工不改接口，作废会白白丢掉下游已经做完的工作。但只在「新交接出现」时才通知，留了两个缺口，各补一个不拦截的措施：

1. **缺口一：打回到新交接之间这段时间，下游并不知情。** 补法：人在面板上打回上游时（`decide(reject)`，而且被打回的阶段或返工目标正好是某个已开工下游所依赖的阶段），立刻给下游发一封预告信，主题「上游返工：T1@implement → T2」，正文写打回原因（blocking 编号和问题），末句「上游正在返工，新交接出来时会再通知你」。这样下游能自己决定先停在接口附近，还是继续做。
2. **缺口二：下游可能先于上游返工完成，按过期的上游交接走完审查、被批准。** 补法：
   - 下游审查信的 `upstream_changes` 除了列已有的新交接，再加 `upstream_state`：上游该阶段当前是 reworking、superseded 还是 current；
   - 下游最后一个审批门的审批卡上显示一条 scope_notes 风格的提示：「依据的 T1@implement 已有更新 / 正在返工」；
   - 都不拦截，由人决定批不批。

有了预告、审查时的状态和审批卡提示，「不作废」就够了。

### ② 预览提示怎么定，才不会天天误报？

原则：**提示以模拟中真实出现的等待为准，不看静态结构。** 只看参与这次会议的成员，并且只有多于 1 个任务时才算。具体每条：

- **`single_coder`：** 实现阶段有 2 个及以上，全部属于同一个人，同时至少有一位别的参与者只做审查。只有一个实现任务的计划不提示。
- **`serial_chain`：** 我改为采纳 codex 的结构定义：任意两个任务都能经依赖排出先后。另加门槛：任务数 ≥ 3。原因是「代码 → 文档」这种 2 任务的计划，本来就该串行，每次都提示就是误报。我原来「每波只有 1 项」的定义会被审查阶段干扰，放弃。
- **`owner_queue`：** 模拟里某个任务在第 w 波依赖已满足、租约也空，只是负责人正忙；同时在第 w 波有另一位参与者完全空闲。两个条件都成立才提示。负责人名下有两个任务、但另一位也满员时不提示。这是和 codex 版本最大的分歧：codex 的版本只要「同一负责人名下有互不依赖的任务」就提示，正常的两人各领两个任务的计划都会被报。
- **`path_serialized`：** 同理，只有模拟中真的因租约推迟了，才提示，并列出冲突的 glob。

每条提示都带 `code`，文案以「（仅提示）」开头。

### ③ smoke 分模块、临时租约接入 smoke.ts 可行吗？

可行，但步骤要写死。我核对了 `leases.ts` 和 `scopeAndCommit`：

- `reserve_paths` 在任务进行中申请的租约带 `task_id`，会进入本任务的 ownGlobs，所以交接时会被提交；
- 但这份租约要到**任务结束**（审查批准）才自动释放。如果不手动释放，它会一直挡住另一个任务改 smoke.ts；
- 反过来，如果在交接之前就释放，此时另一方恰好又租着它，你声明的 smoke.ts 会被判成「属于其他任务的租约，没有提交」。

所以 codex 说的顺序是对的，写进纪要：

```
reserve_paths(["scripts/smoke.ts"])
→ 只加一行 import 和调用
→ files_changed 写上 scripts/smoke.ts
→ submit_handoff
→ 看返回的 commit 确认已提交
→ release_paths(["scripts/smoke.ts"])
```

返工需要再改时重新申请。租约冲突时等对方释放，不要硬改。

备选：smoke.ts 自动发现 `scripts/*-smoke.ts`，这样谁都不用改它。但这一版本来就想实测临时租约，所以只作为备选。

## 1. 上游打回后，下游能否继续

可以继续。只在接口已够稳定、两边有独立文件范围、下游允许局部返工时用 `@stage`。对发布、数据迁移或必须以已审定接口为准的任务，计划直接写 `T1`，等上游整任务完成。这样早开工是规划者的显式选择，不会给所有下游加一轮等待。

同意 Claude 用最新 attempt 的实际交接放行 pending 任务，并把下游开工所用的 handoff ID 和 SHA 固定下来。上游返工时，已经 active 的下游继续用原快照，尚未启动的等当前合格交接。对有审批门的审查阶段，`awaiting_approval` 仅在审查 verdict 为 approve 时提前放行，`approved` 则尊重人的最终决定。无审批门的 `done` 沿用现有推进语义。即使上游已经 done，也要能找到指定阶段的交接，避免下游没有可追溯的基线。

我修正上一轮只在新交接时发信的方案。审查人提交 reject 时先等人的决定。人确认打回、返工会回到依赖阶段或更早阶段时，发一次「上游返工」信，说明当前基线及返工原因，提醒下游暂缓依赖未定接口的那一部分。有新交接时再发「上游变化」信，给出基线和新 SHA、摘要及改动文件，交由下游判断是否跟进。两封信都用 system、无需确认，按下游任务、依赖和触发的 attempt 或 handoff 去重。负责人收到信。当前已有审查人取信时，同一事件也通知这个审查人。尚未取信的审查直接在任务信看到 `upstream_changes`，审查时核对与最新上游的兼容性。在下游已经提交、仍等人工审批的窗口，审批卡至少要能显示有更新，避免审查人刚交接就出现看不见的新基线。运行整体停止时上下游一起结束，不用发继续工作的通知。

Claude 指出现版没有单任务取消属实。我的上一轮草案加了任务卡操作，但这会引入取消传播和 ACP 租约的额外状态，建议本轮先锁定取消通知的格式、共用入口和覆盖用例，定稿明确现有面板只能停止整个运行。若定稿坚持用户可触发单任务取消，再把操作和 pending 后继收敛放进明确的任务验收，避免宣称已有入口。

校验建议接受 Claude 的补充。同一上游写重复依赖时给出明确报错，含同时写整任务和阶段依赖。阶段依赖的两侧都声明文件范围，已有 `globsOverlap` 判定重叠时列出冲突的 glob。解析、实际模板和调度判断统一复用。审查优先沿用 `on_reject`、同类按 attempt ID，已发和在做的信不换；同次调度里可一起就绪的候选先收全再挑。

## 2. 预览怎样少误报

同意按实际模板展开，每阶段 1 单位，成员同波只能做一项，按真实租约和审查优先模拟。卡上显示分波、实现与审查数，说明估算未计入审批等待及返工。建议四条提示用以下规则，每种原因合并展示。

- `single_coder`：确实只有一个成员承担实现，且有另一位会议成员只分到审查时提示，并列出名字。只有一位参与者的计划不触发。
- `serial_chain`：至少两项任务，且任务之间的阶段先后关系使每对任务都必须等前者做完，同时模拟结果每波只有一个阶段，才称为「串行链」。仅仅所有波都是单人，可能是成员或租约的限制，按具体原因提示。能重叠执行的 `@stage` 链不触发。
- `owner_queue`：两项之间双向没有依赖路径、文件范围互不冲突，且两个实现阶段在同一波确实可以领取，只因同一个成员只能做一项而顺延。只列真正被顺延的任务，避免把各有不同前置条件的任务误报为排队。
- `path_serialized`：不同成员的任务在同一波已满足启动条件，且实际因文件租约重叠无法同时启动时提示，列出冲突文件范围。依赖本来就把两项排开时不提示。

同意 Claude 提议的结构化提示码和纯函数。保留我上一轮关于预览一致性的建议：定稿回执和审批卡读同一份结果，重开历史轮次也能看到当时的估算。提示不阻止提交。验收加两项反例：同一负责人各自等待不同前置时无 owner_queue；一条 `@implement` 链实际能同波做两个阶段时无 serial_chain。

## 1. 阶段依赖、投递和交接

### 1.1 格式与拒绝条件

`depends_on` 每项严格匹配 `^[A-Za-z0-9_-]+(?:@[A-Za-z0-9_-]+)?$`，大小写精确匹配。旧格式 `T1` 等上游任务 done。新格式 `T1@implement` 等上游指定阶段的交接。依赖解析、校验、调度和预览共用解析规则。

定稿逐项报错，指出下游任务、原依赖项和原因。拒绝以下情况。

1. 格式不符，例如 `T1@`、`@implement`、`T1@a@b` 或含空白。
2. 引用不存在的任务，或引用自己。
3. 同一个下游重复引用同一上游，包括重复同一项、混用 `T1` 和 `T1@implement`，或同时写同一上游的两个阶段。
4. 引用上游实际没有的阶段。按 `templateStages(owner, reviewer)` 展开，列出可选阶段。模板裁去无审查人任务的 review 时，给出专门原因。
5. 依赖成环。检查时把带 @ 的引用投影到上游任务，返回环路。
6. 阶段依赖的任一方没有规范化后的有效 `paths`，或上下游范围按现有 `globsOverlap` 判定重叠。冲突时列出两侧 glob。整任务依赖允许复用文件范围。

### 1.2 放行、基线和审查优先

阶段依赖必须有指定阶段的实际交接。取该阶段最新 attempt，其状态须为 `done`、`awaiting_approval` 或 `approved`。若是有审批门的审查（`on_reject` 有值）且仍处于 `awaiting_approval`，交接须为 `verdict: approve` 才提前放行。已经 `approved` 尊重人工决定，非审批阶段沿用 `done` 语义。上游取消时不放行新的下游。人确认打回且返工目标在引用阶段或之前时，未启动的下游等待该阶段的新合格交接。任务已 done 也要找到实际的指定阶段交接。

交接落库并更新 attempt 状态后立即重调度，有无审批门均覆盖。人工批准或打回更新后重调度。下游拿到租约、由 pending 转 active 时持久化任务基线，重启和补发信件沿用原值。任务信的 `dependencies[]` 对每条阶段依赖附 `based_on: { stage, handoff_id, commit }`。每份下游交接由桥写入 `data.based_on: [{ dep, stage, handoff_id, commit }]`。无 Git 提交时 `commit` 为 null，交接 ID 仍能准确定位。旧任务没有这些字段时按原行为读取。文件夹的等待原因与调度共用依赖判断。

成员没有在做的阶段、也没有已发任务信时，待投递的 `ready` 审查（`on_reject` 有值）先于实现，同类按 attempt ID 从小到大。一次调度先收齐当次候选，再给各成员投递。已发和已取的信照常进行。

同一工作树的桥内交接将读改动、选路径、提交、读取 SHA 放在同一个串行临界区，保持每个 attempt 原有的防重复提交行为。排队期间已停止或替换的 attempt 在开始 Git 操作前重新核对。并发 smoke 同时提交两项，核对各自的 Git 结果、SHA 和文件。

### 1.3 上游通知和审批提示

已经 active 的下游保留开工基线、租约和阶段。审查人提出 reject 时先等待人工决定。人确认打回，且被打回的就是引用阶段或将返工到引用阶段及其之前时，发「上游返工」。被引用阶段有新交接落库时发「上游变更」。单独上游取消时的事件和信件格式共用同一入口。0.12 的实际停止操作仍然是整轮停止，所有任务先标记取消，已结束的下游不会收到继续工作的信。单任务停止另行设计。

信件固定为 `kind: system`、`from: bridge`、`ack_required: false`。收件人为下游负责人，当前审查人已领取该下游阶段时也送给该审查人，两者相同则只送一次。邮件 ID 固定为 `upstream:<run_id>:<downstream_task_id>:<dep>:<event>:<event_id>:<recipient>`。event 为 `rework`、`change`、`cancel`，event_id 分别取被打回的 attempt ID、新 handoff ID、被取消的上游 task ID。

三类主题分别为 `上游返工：T1@implement → T2`、`上游变更：T1@implement → T2`、`上游取消：T1@implement → T2`。正文按以下顺序，SHA 缺失或没有文件时对应值写「无」。

```text
运行 #<run_id>
上游 <任务ID>「<标题>」 阶段 <stage> → 下游 <任务ID>
开工依据 <基线SHA或无>（交接 #<基线handoff_id>）
新交接 <新SHA或无>（有新交接时附 #<handoff_id>）
摘要 / 原因 <交接摘要、打回理由或取消原因>
改动文件 <新交接的文件列表或无>
<按事件使用以下固定末句>
```

- 返工末句「上游正在返工，新交接出来时会再通知你。你可以先处理不依赖该接口的部分。」打回原因包含人工备注和已有阻塞编号及问题。
- 变更末句「请判断改动是否影响你的任务。需要跟进就修改，否则继续。」
- 取消末句「请判断是否仍可继续。需要调整时请向用户说明。」

任务信带 `upstream_state`，按依赖列出 `current | reworking | superseded | cancelled`。有新交接时附 `upstream_changes`，按 handoff ID 列出开工以后被引用阶段的交接，包含 `dep`、`based_on_handoff_id`、`based_on_commit`、`handoff_id`、`commit`、`summary`、`files_changed`。仍待补齐合格交接的返工显示 reworking，返工后基线已有新合格交接显示 superseded，取消状态优先。审核人按此核对与上游的兼容性。下游待审批时，审批卡直接显示「依据的 T1@implement 正在返工／已有更新／已取消」的适用提示，由人决定是否批准。

## 2. 长命令心跳

`report_progress(agent_id, text, busy_minutes?)` 的时长是 **1–60 的整数分钟**。不接收小数、字符串或越界值。传入时必须有已领取的 `in_progress` attempt，期限绑定到该 attempt 和 MCP 绑定。重报带时长则从这次汇报起覆盖，省略时长则清除。成功交接、attempt 结束或取消、绑定释放或替换、到期和守护进程重启时清除或失效。交接因校验被拒时保留时限。

`sweep` 只在匹配的 fetched、需确认的任务信上应用时限，原有取信及最近活动的确认窗口保持有效。超过原有截止且当前时间达到 `busyUntil` 才正常报 `ack_overdue`。会议信沿用原规则。Office 与成员详情在有效期内显示「正在执行长命令，预计 HH:mm 前」，由本地时间渲染 `agents[].activity.busy_until` 的 ISO 时间，到期及时恢复。工具描述和 join 加上「预计超过 5 分钟不调用桥工具时，先 report_progress 并带 busy_minutes」。

## 3. 并行预览

用纯函数按实际模板展开阶段，每阶段计 1 单位，每个成员每波最多一个阶段。按审查优先和任务清单顺序稳定排队，模拟任务级租约，阶段交接在该波结束后可供后续波使用。预览按无返工的正常推进估算，审批等待不计时间。输出 `waves`（每波的任务、阶段、成员）、`members`（每人的实现与审查数）、`total_units` 和 `hints: [{ code, text }]`。定稿工具回执返回 preview，同一份结果随定稿轮保存，审批卡及完整历史轮次读取它。旧定稿可以没有 preview。定稿指引和 MCP 参数说明一并补上写法、限制和两位主力各领一个并行实现任务并交叉审查的要求。

以下为四类提示，每类合并具体成员或任务，附「仅提示」，不拦截定稿。

- `single_coder`。至少两项任务的实现都落在同一成员，全部实现阶段也由此人承担，且另一位本次会议的参与者有审查分配而没有实现分配。显示对应成员。单任务计划不提示。
- `serial_chain`。至少三项任务，任意一对均有前者全部完成才能启动后者的依赖关系。只因成员或租约排成单人波次时用对应提示。允许重叠的阶段依赖链不提示为整任务串行链。
- `owner_queue`。两项无依赖关系、范围不冲突的实现任务在同一波实际可领取，因同一负责人已经在做另一项实现而顺延，且本轮另一位参与者在该波完全空闲。两位都排满时不提示。

## 1. commit_note 的判断规则（T1）

- 判断放在服务端，写成一个函数 `commitView(h)`，放在 `room.ts`。`/api/state`、文件夹接口和 `/classic` 都用它，面板不自己猜。
  - `commit_sha` 有值：两个字段都为 null；
  - 否则，`commit_error` 以「未提交：」开头（全角冒号，精确前缀匹配）：`commit_note` = 原文，`commit_error` = null；
  - 否则，`commit_error` 非空：这是 0.13 之前的真实错误，保留在 `commit_error`，`commit_note` = null。
- 结论：`commit_note` 用中性样式（灰色，`muted`），`commit_error` 继续用 `bad`/`form-error`。数据库不改。`submit_handoff` 返回的 `commit_note` 保持不变。
- 要改的四处：`handoff.js:52`、`folder.js:64`、`v1/room.js:203`、`panel.ts:145`。`v1` 和 `classic` 读的也是同一份投影字段，各自都能分清这两种情况。
- 依据：`f5ea68b` 之后，桥只会写入「未提交：…」的跳过原因，所以前缀足以区分。旧库里的真实错误不会以这个前缀开头。

## 2. /api/state.daemon 字段（T2）

```
daemon: {
  version: string,              // 守护进程启动时读到的 package.json version
  commit: string | "dev",       // 从 dist 运行时取 build-info.commit；从 src 用 tsx 运行时固定为 "dev"
  dirty: boolean | null,
  channel: "release" | "main" | "dev",
  built_at: string | null,
  started_at: string,           // ISO
  project: string,
  port: number,
  install_dir: string           // 包根目录
}
```

- 从源码运行时 `commit` 写 `"dev"`。原因：同一工作树里可能残留旧的 `dist/build-info.json`，照读会显示一个过期的提交号。判断方法：`import.meta.url` 落在 `/src/` 下。
- 这些值在启动时只读一次，之后不变。

## 3. update 的通道参数（T2）

- `ai-bridge update [--channel release|main] [--ref <ref>] [--force] [--dry-run]`。
- 默认 `--channel release`：
  1. 请求 `GET https://api.github.com/repos/<REPO>/releases/latest`；测试时可以用环境变量 `BRIDGE_RELEASE_API` 换成本地的假服务；
  2. 取资产里唯一一个 `ai-bridge-<版本>.tgz`，版本必须等于 tag 去掉开头的 `v`；
  3. 下载到临时目录，然后 `npm install -g <tgz>` → `setup --refresh` → `doctor`；
  4. 已安装版本和 Release 版本相同、而且已安装的是 release 通道时跳过，除非加 `--force`；
  5. 以下情况都在执行 `npm install -g` 之前报错退出，旧安装保持不动：
     - 没有 Release；
     - 没有匹配的资产，或者有多个；
     - 下载失败；
     - 版本对不上。
- `--channel main`：沿用现在的做法，fetch → npm ci → pack → install；`--ref` 只在这个通道有效。单独写 `--ref`（不写 channel）等同于 `--channel main`，写 `--channel release --ref` 直接报错。
- **通道写进安装包**：`build-info.mjs` 读环境变量 `BRIDGE_BUILD_CHANNEL`，可以是 release、main 或 dev，默认 dev。`release.mjs` 打包时设为 release，`update --channel main` 设为 main。`doctor` 按通道比较新旧：
  - release 通道：和最新 Release 的版本比；
  - main 通道：和 main 的提交比（第 21 节）；
  - dev：只显示，不比较。
- **doctor 新增一节「运行中的桥」**：
  - 读 `/api/state.daemon`，和 CLI 自己的 version、commit 对照；
  - 不一致时显示 `✗`，并提示「停掉 ai-bridge 后重新 ai-bridge start」；
  - 0.12 及以前的守护进程没有这个字段，显示「运行中的桥版本未知（0.12 或更早），建议重启」。

## 4. release.mjs 的检查项（T2）

`node scripts/release.mjs [--dry-run]`，依次执行，任何一步失败都以非 0 退出：

1. `package.json` 的 version 和 `package-lock.json` 根包的 version 一致，并且是合法的 semver；
2. `CHANGELOG.md` 里有 `## <版本>` 或 `## [<版本>]` 小节，而且内容不为空；
3. 工作区干净：`git status --porcelain` 为空，未跟踪的文件也算；
4. 本地和远端都还没有 tag `v<版本>`；查远端用 `git ls-remote --tags`，查不了就只给警告；
5. 运行 `npm run typecheck`、`npm run build`、`npm run smoke`；`--dry-run` 时跳过，打印「会运行」；
6. 设 `BRIDGE_BUILD_CHANNEL=release` 后 `npm pack --pack-destination release/`。然后解开安装包核对三件事：
   - 有 `dist/build-info.json`，`channel` 为 release、`commit` 等于 HEAD、`dirty` 为 false；
   - 带有 `README.md`、`README.en.md`、`CHANGELOG.md`；
   - `--dry-run` 时只列出会打包的文件（`npm pack --dry-run --json`）；
7. 把该版本的 CHANGELOG 小节写到 `release/notes-<版本>.md`；
8. 打印 `gh release create v<版本> release/ai-bridge-<版本>.tgz --title "ai-bridge <版本>" --notes-file release/notes-<版本>.md`。**永远不执行**。

另外，`package.json` 的 `files` 要加上 `CHANGELOG.md`、`README.en.md` 和 `docs/images`（README 引用截图）。这个改动由 T2 做，因为版本相关的文件归 T2 管。

## 2. /api/state.daemon（T2）

```
daemon: {

  commit: string,                  // 完整 SHA；从 src 用 tsx 运行时为 "dev"
  dirty: boolean | null,           // 源码运行为 null
```

## 3. update 的通道参数（T2）

`ai-bridge update [--channel release|main] [--ref <ref>] [--force] [--dry-run]`

- **通道选择**：
  - 默认是 `release`；
  - 单独写 `--ref`、没有写 `--channel` 时，按 main 处理，和以前的行为一致；
  - `--channel release` 和 `--ref` 同时出现，或者 `--channel` 写了未知值，直接报错退出。
- **release 通道**，按顺序执行：
  1. 请求 `GET <API>/repos/<REPO>/releases/latest`。`<API>` 默认是 `https://api.github.com`，可以用环境变量 `BRIDGE_RELEASE_API` 替换成本地的假服务；
  2. 在资产里找唯一一个文件名等于 `ai-bridge-<版本>.tgz` 的安装包，其中「版本」是 tag 去掉开头的 `v`。匹配规则写在 `src/release-asset.ts`，和 release.mjs 共用；
  3. 下载到临时目录，解开后逐项核对：包内 `package.json` 的 name 是 `ai-bridge`、version 等于 tag 的版本；`dist/build-info.json` 存在，`channel` 为 release，`commit` 不为空；
  4. 全部通过后，才执行 `npm install -g <tgz>`，然后 `ai-bridge setup --refresh`，再 `ai-bridge doctor`；
  5. 已安装的是同一个版本、channel 也是 release 时跳过，`--force` 可以强制重装。
- **失败时**：没有 Release、资产缺失或不止一个、下载失败、任何一项核对没通过，都在全局安装之前报错退出，旧安装不动，**不自动改用 main**。
- **main 通道**：保留现在的流程（临时检出 → `npm ci` → pack → install），只是给 `npm ci` 加上 `BRIDGE_BUILD_CHANNEL=main`。
- **测试**：用离线夹具（本地 HTTP 假服务加一个假的 npm），断言失败时全局安装命令一次都没有被调用。

## 4. release.mjs 的检查项（T2 实现，T3 做整仓预检）

`node scripts/release.mjs [--dry-run]`。任何一项失败都以非 0 退出，打印失败原因。

**两种模式都做的预检**，可以离线重复运行：

1. `package.json` 的 version 是合法的 semver，而且和 `package-lock.json` 根包的 version 一致；
2. `CHANGELOG.md` 里有 `## <版本>` 或 `## [<版本>]` 小节，并且内容不为空；
3. 工作区干净：`git status --porcelain` 为空，未跟踪的文件也算。

**`--dry-run`**：预检之后不再执行，只打印接下来会做的步骤和那条 `gh` 命令。文件清单在临时副本里用 `npm pack --dry-run --json --ignore-scripts` 列出，不在工作树里触发 prepare。

**正式模式**，在预检之后继续：

4. 本地还没有 tag `v<版本>`。远端 tag 用 `git ls-remote --tags` 查，只作附加诊断，查不了时给警告，不算失败；
5. `npm run typecheck`、`npm run build`、`npm run smoke`；
6. 用 `BRIDGE_BUILD_CHANNEL=release` 执行 `npm pack --pack-destination release/`，然后读实际生成的 tgz 核对：
   - 包名和版本；
   - `dist/cli.js`、`dist/daemon.js` 这类入口文件都在；
   - `README.md`、`README.en.md`、`CHANGELOG.md` 都在；
   - README 引用的 `docs/images/*` 都在；
   - `dist/build-info.json` 的 `channel` 是 release，`commit` 等于 HEAD，`dirty` 是 false；
7. 把本版本的 CHANGELOG 小节写到 `release/notes-<版本>.md`；
8. 打印 `gh release create v<版本> release/ai-bridge-<版本>.tgz --title "ai-bridge <版本>" --notes-file release/notes-<版本>.md`，**永不执行**。

`package.json` 的 `files` 加上 `CHANGELOG.md`、`README.en.md` 和 `docs/images`，由 T2 改。T2 用临时夹具验证通过和被拒绝的各种情况。真正在本仓库跑一次 `release.mjs --dry-run`，等 T3 写完文档后由 T3 来做。

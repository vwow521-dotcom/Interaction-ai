## claude 提案：0.11 审查效率

我读了 `store.ts` 里的 `HandoffData` 和 `Feedback`，`scheduler.ts` 里的 `turnPayload`、`submitHandoff`、`decide`，`mcp.ts` 里的 `submit_handoff`，还有三个面板里用到 `blocking` 和 `review_comments` 的地方。总体同意草案的方向。下面先给 T1 的接口方案，要求写死的部分都标了出来。再说明我对草案改了哪几处、为什么改。

### 1. 关键决策

**D1. 不新建表，问题台账从交接数据推导出来。**
- 每个 issue 存在提出它的那份审查交接的 `data.issues` 里。
- 每次复核存在当轮审查交接的 `data.rechecks` 里。
- 新增一个纯函数 `issueLedger(taskId)`，在 scheduler 或 store 里都行。它按 id 顺序遍历这个任务的所有交接，返回 `[{ id, problem, repro, raised_handoff, status, history }]`。status 取四种：`open`、`fixed`、`not_fixed`、`waived`。
- 理由：不用迁移，也不用维护两份状态。0.10.1 的旧库不受影响。smoke 可以直接对这个函数断言。面板也用它来统计。

**D2. 编号格式写死为 `<task.key>-B<n>`。**
- 单任务的流水线运行也用 `T1-B1`。
- n 是这个任务已有编号里最大的序号加 1，从 1 开始，返工多少轮都不会重号。
- 编号只由桥分配。agent 传进来的 id 字段会被 zod 剥掉。

**D3. `issues` 不要 `ref` 字段，`rechecks` 是引用旧问题的唯一途径。**
- 草案里 issue 的 `ref` 和 `rechecks` 功能重叠，同一件事有两种说法，校验会变复杂。
- 所以 `issues` 里只放新问题。上一轮的问题没修好，要补充说明的话，写在 `rechecks[].note` 里。

**D4. 只有带 `verdict: reject` 的审查才会给问题编号。**
- 旧写法 `review_comments` 搭配 `approve`，沿用现在 `decide` 的行为，当作观察，不编号。
- 新参数 `issues` 搭配 `approve` 直接拒绝提交，提示把这些内容写进 observations。

**D5. 人在面板上点「批准」通过一份 reject 审查时，这份审查留下的 open 和 not_fixed 问题记为 `waived`（豁免）。**
- 理由：如果流水线后面还有别的审查阶段，它不应该被迫复核已经被人放行的问题。
- 这个状态由 ledger 推导：看最后一次涉及该问题的交接，它所在 attempt 的状态是 `approved`，同时 verdict 是 reject，就是 waived。不用回写数据库。

**D6. `Feedback.blocking` 改成 `Issue[]`，旧面板做一行兼容。**
- 不另加一个并列字段，否则同一批内容会在载荷里出现两次，违背第 24 节的去重。
- `panel.ts:246` 和 `panel/v1/room.js:209` 原来直接 `concat` 字符串，要改成 `typeof i === "string" ? i : i.id + " " + i.problem`。这一处修改归 T2。
- `parseFeedback` 读旧库时，把字符串 `blocking` 转成 `{ id: null, problem }`。

**D7. 共享工作区在取信时懒创建。**
- 在 `readTaskMail` 和 `turnPayload` 里 `mkdirSync(recursive)`，不在 `schedule` 里创建。
- 理由：升级前就已在进行的任务也能拿到目录，而且只有一个创建点。
- 任务结束后不清理，0.11 不做清理功能。

### 2. T1 接口（定稿时照抄）

```ts
// store.ts
interface Repro { command: string; cwd?: string; expect: string }   // cwd 相对项目根，可以写 shared_dir
interface Issue {
  id: string | null;          // 桥分配 "T2-B3"；旧数据为 null
  problem: string;
  repro?: Repro;
  late_reason?: string;
  raised_round: number;       // 第几次审查提出（这个任务的审查交接序号，从 1 开始）
  late?: boolean;             // 桥算出：非首次审查提出、又没写 late_reason
}
interface Recheck { id: string; status: "fixed" | "not_fixed"; note?: string }
interface Addressed { id: string; how: string; verified?: string }
HandoffData += { issues?: Issue[]; rechecks?: Recheck[]; addressed?: Addressed[] }
Feedback.blocking: Issue[]    // 来自打回：新问题 + not_fixed 的旧问题；carried 时每项再并入 addressed（见下）
```

**MCP 输入**（`mcp.ts`）：
- `issues: [{ problem, repro?: { command, cwd?, expect }, late_reason? }]`
- `rechecks: [{ id, status, note? }]`
- `addressed: [{ id, how, verified? }]`

以上三项都可选。`review_comments` 保留，标注为「旧写法」。

**校验在 `scopeAndCommit` 之前做。**校验失败时不提交 git，也不确认信件。

阶段的判定：
- 审查阶段 = `stage.on_reject` 有值，或者传了 `verdict`。
- 非审查阶段传 `issues` 或 `rechecks` 都会被拒绝。

拒绝条件（照抄）：

| # | 条件 | 错误信息要包含 |
|---|---|---|
| R1 | 审查阶段的交接中，`rechecks` 没有覆盖 ledger 里所有 status 为 open 或 not_fixed、且 id 不为空的问题 | 缺的编号列表 |
| R2 | `rechecks` 里有未知编号或重复编号 | 这些编号 |
| R3 | `verdict: reject`，但既没有任何 `not_fixed`，也没有新问题（`issues` 和旧写法的 `review_comments` 都算） | — |
| R4 | `verdict: approve`，但带了 `issues`，或者有 `not_fixed` | 让对方改成 reject，或者写进 observations |
| R5 | `repro` 里有 `command` 但没有 `expect` | 由 zod 保证 |
| R6 | 非审查阶段传了 `issues` 或 `rechecks` | — |

不拒绝、只记录的情况：
- 新问题出现在非首次审查里，又没写 `late_reason`：设 `late: true`，审批卡上标出来。
- 返工交接漏写了 feedback 里某个编号的 `addressed`，或者写了未知编号：加一条 `scope_notes`，例如「addressed 未说明：T2-B1」。

**旧写法换算。**`review_comments` 搭配 `reject` 时，每条字符串转成 `{ problem }`，和 `issues` 合并后统一编号。

**`review_comments` 字符串照旧写入 `data`**，旧面板和 git 提交信息不用改。
- 新问题写成 `T2-B3 问题描述（复现：命令 → 期望）`。
- 没修好的旧问题写成 `T2-B1 [未修复] 问题描述`。

**载荷。**
- **返工信**：`feedback.blocking` 带上编号和 repro，说明文字加上「提交前逐条运行 blocking[].repro，确认结果符合 expect；在 addressed 里按编号写怎么处理的、跑了什么」。按第 24 节的去重，`input_handoff` 去掉 `review_comments`、`observations`、`issues`、`rechecks`。
- **复审信**（carried）：`feedback.blocking` 改为取 ledger 里所有 open 和 not_fixed 的问题，每项并入返工方的 `addressed: { how, verified } | null`。`input_handoff` 去掉 `addressed`，不重复发送。说明文字写「rechecks 必须覆盖 feedback.blocking 里所有带编号的项，否则提交被拒」。
- 所有任务信都带上 `shared_dir`（相对路径，例如 `.bridge/shared/7/T2/`）。

### codex

## 提案

把每次审查结果写进该次交接 JSON，由任务历史分配编号，沿用人工审批决定是否推进或返工。当前 `scheduler.ts` 已按任务读取有序交接记录并串行提交，同一问题可在几轮交接间引用同一编号，复审卡也能回看当时的结论。建议定稿锁定下面的接口。

### T1 接口和状态

- `submit_handoff.issues?: [{ problem, repro?: { command, cwd?, expect }, late_reason? }]`。每项只创建一个新问题。`problem`、有 repro 时的 `command` 和 `expect` 必须是非空字符串，`cwd` 省略时取项目根目录，提供时为项目内相对目录。建议草案删掉 `ref`，已有问题统一通过 `rechecks` 引用；明确拒绝输入项携带 `ref` 或自行指定 `id`，避免两条路径对同一问题给出冲突结论。复审中新问题的 `late_reason` 缺失或空白，落审批提示，仍可提交。初审的新问题无需写理由。
- `rechecks?: [{ id, status: "fixed" | "not_fixed", note? }]`。复审的基准为回到原审查阶段时 `feedback.blocking` 中仍未关闭的问题。每个编号恰答一次，缺失、重复和未知编号均拒绝并列出编号；`approve` 只允许全部 `fixed` 且没有新问题；`reject` 至少有一项 `not_fixed` 或一项新问题。结构化审查字段要求有 `verdict`，有待核对项的复审也必须带 verdict。初审可以不传 rechecks。所有硬校验在尝试 git 提交、写交接、确认来信和推进状态之前完成，失败后仍可重新提交。
- 返工交接 `addressed?: [{ id, how, verified }]`，其中 `how` 和 `verified` 是非空字符串，写清处理方式、执行命令和实际结果。无法执行时照实记录原因，便于复审方补验。漏项、未知编号或重复编号在 `scope_notes` 提示，未知编号及重复组不进入复审证据，返工仍可交接。返工信指向 `feedback.blocking[].repro`，逐条自查；复审信将有效自查记录放在对应 `feedback.blocking[].addressed: { how, verified }`，同时从该信的 `input_handoff` 省去已投影的 `addressed`。
- 存储 `data.issues?: [{ id, problem, repro?, late_reason?, added_in_recheck: boolean }]` 和 `data.rechecks?: [{ id, status, note?, issue }]`，`issue` 是当轮采用的问题快照，交接历史与审批卡可直接渲染。任务内按新增顺序分配 `<task.key>-B<正整数>`，由同任务已保存的编号和旧审查记录决定，按最大序号加一；复查旧项沿用原编号。人确认打回时，下一轮 `feedback.blocking` 取 `not_fixed` 的旧项加本轮新项；通过或人工覆盖沿用现有审批语义。返工信从被打回的 `input_handoff` 省去 `issues/rechecks/review_comments/observations`，复审继续省去上轮 observations。历史、审批卡及上下文保留交接原始记录。
- 兼容 `review_comments: string[]`：只传旧字段且 verdict 为 reject 时，每条按原顺序生成 issue；两种新问题来源都非空时明确拒绝并请选一种。继续保存字符串版 `review_comments`（本轮未修复和新增的编号加描述），维持 Git 提交正文及旧卡片；历史 approve 的旧意见仍按现有语义处理。以旧字段提交全新一轮仍可打回；进入有待核对编号的复审后，旧字段可报新问题，逐条核对也必须提交。升级时按同任务旧审查交接顺序及原条目序号确定性补出旧编号，在读边界把活动返工或复审的 `blocking: string[]` 对回来源交接，避免重启或重复描述改变编号。旧记录缺来源时按原条目顺序补号，活跃流程的后续分配计入这些编号。工单口径包含运行号，跨 run 的同名任务独立编号。

### deepseek

# 0.11 审查效率提案（deepseek）

读了 0.11 prompt、`scheduler.ts`（turnPayload/submitHandoff/decide）、`store.ts`（HandoffData/Feedback/表结构）、`mcp.ts`、`room.ts`、`handoff.js`、smoke B/D 段，以及 ARCHITECTURE §19/§24。核心判断：**0.11 不需要新表，也不需要调度器大改；它需要的是一份写死的接口契约 + 追加式历史 + 状态派生。**

## 一、总体思路

1. **追加式历史。** 审查交接单新增 `issues`（本轮新增的阻塞问题），复审交接单新增 `rechecks`（对上一轮每个编号的逐条结论），返工交接单新增 `addressed`（每项怎么改的、跑过什么）。
2. **状态派生，不建新表。** 创建下一次 attempt 时，由桥计算「仍未关闭的问题」= 本 attempt 收到的 `feedback.blocking`（上一轮未关闭）− `rechecks` 里 fixed + 本轮 `issues`。handoff 本来就是按任务追加的事实源；独立 issues 表会多一套迁移和两份可能不一致的状态。重号风险用「按该任务历史 handoff 里的最大编号 +1」消除，不需要计数器列。
3. **校验先于提交。** 所有拒绝条件放在 `scopeAndCommit` 之前：被拒的提交不产生 commit / handoff，重试时按同一历史重新编号（幂等）。
4. **兼容只保留在读路径。** 旧 `review_comments` 字符串、旧 `feedback.blocking` 字符串继续可读；主面板显示编号和 repro，`/v1`、`/classic` 靠派生的字符串照常显示。

## 二、定稿必须写死的契约

```ts
interface Repro { command: string; cwd?: string; expect: string } // cwd 相对项目根，缺省项目根
interface Issue { id?: string; problem: string; repro?: Repro; late_reason?: string }
interface Recheck { id: string; status: "fixed" | "not_fixed"; note?: string }
interface Addressed { id: string; how: string; verified?: string }

HandoffData 新增（全部可选，不破坏旧客户端）：
  issues?: Issue[]        // 仅审查阶段；每一项是「本轮新增」，id 由桥分配，调用方不得填
  rechecks?: Recheck[]    // 仅复审阶段；对上一轮仍开放编号逐条回答
  addressed?: Addressed[] // 仅返工阶段；对 feedback.blocking 逐条说明
Feedback.blocking: Issue[] // 不再 string[]；旧库字符串读成 { problem } 且无 id
```

**编号（写死）：** `<task.key>-B<n>`，n 从 1 起按任务递增，返工多少轮都不重号；普通流水线运行的 key 是 `T1`，即 `T1-B1`。分配时机 = 审查提交通过校验后，取该任务历史 handoff 中 `data.issues[].id` 的最大 n + 1，按 `issues` 数组顺序分配。0.11 之前的历史没有问题编号，所以从 B1 开始。

**写入规则（写死）：**
- `data.issues` 只存本轮**新增**问题；`data.rechecks` 存逐条结论。
- `data.review_comments` 由桥派生：**本轮结束后仍开放**的编号问题，字符串形如 `T2-B3：问题描述`（旧库无编号项就是原字符串）。这样旧面板和 git 提交体的语义仍是「必须修改的阻塞问题」，而且能看出还剩什么。
- `feedback.blocking` 用同一份「仍开放」集合，带 `problem` 和 `repro`；返工信据此自查。
- `data.issues` / `rechecks` / `addressed` 在 `input_handoff` 里按 §24 去重：返工信丢掉 `review_comments`、`observations`，同时丢掉 `issues`、`rechecks`、`addressed`；复审信保留上一份实现交接里的 `addressed`（要和对应 issue 并排展示）。

**拒绝条件（写死，全部在提交前返回 `err` 并列出涉及的编号）：**
- V1 审查阶段 `issues[].id` 非空 → 拒绝（编号只能由桥分配）。
- V2 非复审阶段带 `rechecks`（即本 attempt 的 `feedback.blocking` 里没有带编号的项）→ 拒绝。
- V3 复审阶段：`rechecks` 必须恰好覆盖上一轮仍开放的带编号问题，每个编号一次；漏答、重复、未知编号都拒绝并列出缺的编号。
- V4 `verdict: "reject"` 必须至少有一个 `not_fixed`，或至少一个新增 issue；否则拒绝。
- V5 `verdict: "approve"` 不得带新增 issues，且所有 `rechecks` 必须是 fixed（没有 open 项时可不带 rechecks）。
- V6 新增问题的 `problem`（去掉首尾及连续空白后）与某个仍开放问题完全相同时拒绝，并给出已有编号——强制用 rechecks 回答，不让旧问题换个写法再出现。
- V7 非审查阶段带 `issues` → 拒绝（问题只能由审查提出）。
- V8 新问题缺 `late_reason`（复审轮）→ **不拒绝**，记 `scope_notes` 并在面板标「新增·未说明」，只约束审查方式不卡流程。
- V9 `addressed` 的未知编号、漏写编号、非返工阶段使用 → **不拒绝**，记 `scope_notes`。
- V10 只传旧 `review_comments` 时先转成 issues 再走同一套校验；编号照常分配。

**面板字段（写死）：** `room.ts` 的 handoff item 增加 `issue_summary: { previous_open, fixed, not_fixed, added }`（`previous_open = rechecks.length`），交接卡据此渲染一行「上一轮 4 项：已修复 3，未修复 1；新增 2」。新问题列表按编号显示 problem、repro（可复制 command，显示 cwd/expect）、状态「新增」；rechecks 显示「已修复 / 未修复」。

## 三、关键决策与理由

| 决策 | 理由 |
|---|---|
| 不建 issues 表，状态放交接数据并派生 | 免迁移；handoff 是唯一事实源，历史可回放；避免表与交接不一致 |
| 编号按任务历史 max+1，不用计数器 | 无并发写计数器；重试幂等；跨 run 不串号 |
| rechecks 严格、addressed 宽松 | 审阅者的逐条结论是流程闭环的关键；返工方漏写只提示，符合「约束审查方式、不卡流程」 |
| `review_comments` 派生为「仍开放」而非「本轮新增」 | 旧面板/git 提交体语义正确；复审拒绝但无新问题时不会显示空白 |
| 复审的 `feedback.blocking` 在 `decide(reject)` 时按 rechecks 重算 | 这是整条链路最容易写错的一点：不能照抄 review_comments，否则已修复项会永远跟着返工方 |
| `shared_dir` 在任务激活时创建、任务结束保留 | 实现和审查天然共用一份；`.bridge/.gitignore` 已排除，不进 git；清理留到以后 |

### codex

## ① 编号和状态放哪里

同意三方共识：存交接 JSON。T1 保存本轮新问题 `data.issues` 和本轮逐条结论 `data.rechecks`，沿用现有 attempt 的人工审批结果。编号以同一任务已有 `data.issues[].id` 的最大序号加一，从 `<task.key>-B1` 开始。校验通过后分配，现有每 attempt 的提交锁保证同一次交接不会并发占号。旧面板和 Git 正文读派生的 `review_comments: string[]`，内容是本轮仍开放的编号和描述。

- **Claude**：同意人工批准一份 reject 交接时，剩余项可在历史卡显示为「已豁免」，下游无需复核。调度所需的开放集可以直接从本轮反馈计算，下一次返工取本轮 `not_fixed` 旧项加本轮新增；人工批准走现有推进逻辑。任务级全历史台账和 folders API 可暂缓，按交接展示已能覆盖本阶段。建议 recheck 的存储项附一份当轮 issue 快照，卡片打开历史交接时可查看旧项描述和 repro。
- **DeepSeek**：同意追加式历史、开放集计算和把二次打回加进 smoke。建议撤掉「描述相同就拒绝」的 V6。同一句描述可能关联不同的场景或命令，编号才是校验引用的依据。面板统计直接从当前交接的 `rechecks.length`、两种 status 和本轮 `issues.length` 计算，T2 可复用这些字段。
- **修正我首轮的旧库建议**：采用 `{ id: null, problem }` 读取 0.10.1 的字符串，保留文案并要求人工逐项回看；无编号项免严格覆盖，复审发现它仍是阻塞时可在本轮重新提出并获新编号。升级后新提交的 `review_comments` 配合 reject 照常分配编号。旧库无须回填，因此 B1 的起点也清楚。

## ② 复审漏答是否应该拒绝

应该拒绝，范围限于本轮任务信里要求核对的、仍开放的带编号问题。复审方可以先把尚未证实修复的项填 `not_fixed`，用 `note` 指明缺少什么证据，再交人工审批。空着直接提交会让下一轮无法判断该项被修好还是漏验。建议 Claude 在定稿明确以下边界：

1. `issues?: [{ problem, repro?: { command, cwd?, expect }, late_reason? }]` 只报新问题。桥拒绝调用者填写 `id` 或 `ref`。有 repro 时 command 和 expect 必填且非空，cwd 默认项目根目录。非空的 `issues` 与非空的旧 `review_comments` 同时出现时，提示择一提交，避免同一项占两个编号。旧 approve 搭配旧 review_comments 沿用旧语义，意见不获编号。
2. `rechecks?: [{ id, status: "fixed" | "not_fixed", note? }]`。提交结构化审查字段或有待核对项时要求显式 `verdict`，普通实现交接和无待核对项的老流程沿用现有阶段合同。缺失、重复、未知编号均拒绝，并列出各组编号。approve 要求所有待核对项 fixed、没有新 issues；reject 至少一项 not_fixed 或一项新问题。硬校验发生在 Git、写交接和确认收信前，保留当前尝试供重提。复审新问题缺 `late_reason` 只在审批卡提示。
3. 采纳 Claude 和 DeepSeek 的 `addressed?: [{ id, how, verified? }]`。能复现的项写命令和实际结果，未能复现则写原因。漏说明、重复或未知编号只提示；重复组和未知项省去，避免展示错误证据。复审信在对应 `feedback.blocking[]` 附上有效的 addressed，同时省去同一份 `input_handoff.addressed`。旧审查的观察也继续去重。

## 五、定稿建议：冻结契约（相对草案的 delta）

**类型：**
```ts
interface Repro { command: string; cwd?: string; expect: string }  // cwd 相对项目根
interface Issue { id?: string; problem: string; repro?: Repro; late_reason?: string }
interface Recheck { id: string; status: "fixed" | "not_fixed"; note?: string }
interface Addressed { id: string; how: string; verified?: string }
HandoffData += { issues?: Issue[]; rechecks?: Recheck[]; addressed?: Addressed[] }
Feedback.blocking: Issue[]   // 旧库字符串读成 { problem }，无 id
```
输入里 `issues` 不出现 `id`/`ref`（带了就拒绝）；存储的 issue 只加桥分配的 `id`。

**编号：** `<task.key>-B<n>`；范围 task.id；n = 该任务历史 `data.issues[].id` 最大值 + 1；唯一分配点是 `submitHandoff`，校验通过后分配；不追溯旧数据。

**校验（全部在 `scopeAndCommit` 之前，返回 err 并列出编号）：**
1. 审查阶段（`stage.on_reject` 有值或传了 verdict）之外传 `issues`/`rechecks` → 拒绝。
2. `issues` 非空或 `rechecks` 存在 → 必须带 `verdict`。
3. 输入 issue 带 `id`/`ref` → 拒绝；`issues` 与 `review_comments` 同时非空 → 拒绝，二选一。
4. `repro` 有 `command` 必须有非空 `expect`。
5. 复审必须恰好覆盖 ledger 中未关闭且带编号的问题，每项一次；漏答/重复/未知 → 拒绝并列编号。
6. 非复审阶段带 `rechecks` → 拒绝。
7. `reject` 至少一个 `not_fixed` 或一个新问题；`approve` 必须全部 fixed、且无新问题。
8. 新问题文本与未关闭问题完全相同（空白归一化后）→ 拒绝并给出已有编号。
9. 复审轮新问题缺 `late_reason` → 不拒绝，记 scope_notes、面板标「新增·未说明」。
10. `addressed` 漏项/未知/重复/`verified` 空 → 不拒绝，记 scope_notes；未知项不并入复审证据。
11. 旧 `review_comments` + reject → 逐条转 issue 并统一编号；+ approve → observations（沿用当前行为）。

**派生（写死）：**
- `review_comments` = 本轮结束后未关闭的编号问题字符串：`T2-B3：描述（复现：命令 @ cwd；期望：…）`，被 recheck 为 not_fixed 的项加 `[未修复] ` 前缀；旧无编号项保留原字符串。
- `feedback.blocking`：返工 = ledger 未关闭项（含 repro）；复审 = 同一集合 + 每项并入对应 `addressed`，`input_handoff` 去掉 `addressed`。
- 返工信 `input_handoff` 去掉 `review_comments`、`observations`、`issues`、`rechecks`；复审信继续去掉上轮 observations。
- `room.handoff()` 增加 `issue_summary: { previous_open, fixed, not_fixed, added }`；面板统计行 `previous_open = rechecks.length`。
- `shared_dir = ".bridge/shared/<run_id>/<task_id>/"`，取信时幂等创建；失败带 `shared_dir_error`，不阻断阶段。

**smoke 归属：** T1 = 验收 1–5、7 + 非法提交无副作用 + 两次打回；T3 = 验收 6（目录存在、不进 git、阶段共用）；T2 = 面板静态断言 + 7879 手测（打回→返工→复审，编号/repro/统计/复制）。

# 0.11 审查效率：定稿

三轮讨论已经对齐以下几点：
- 不建新表，问题和复核结论写进交接数据。

## 1. 类型（src/store.ts）

```ts
interface Repro { command: string; cwd?: string; expect: string }   // cwd 是相对项目根的路径，省略时为项目根
interface Issue {
  id: string | null;            // 桥分配的编号，例如 "T2-B3"；0.10.1 的旧数据为 null
  problem: string;
  repro?: Repro;
  late_reason?: string;
  added_in_recheck?: boolean;   // 桥写入：在复审中提出的新问题为 true
}
interface Recheck { id: string; status: "fixed" | "not_fixed"; note?: string; issue: Issue }  // issue 是桥写入的当轮问题快照
interface Addressed { id: string; how: string; verified?: string }
HandoffData += { issues?: Issue[]; rechecks?: Recheck[]; addressed?: Addressed[] }
Feedback.blocking: Issue[]      // 读到旧的字符串数组时，每条转成 { id: null, problem }
```

纯函数放在新文件 `src/engine/issues.ts`：
- `nextIssueNumber(task)`：分配下一个编号。
- `validateReview(...)`：执行第 3 节的校验。
- `openAfter(blocking, rechecks, newIssues)`：算出本轮之后仍未关闭的问题。
- `issueSummary(data)`：生成面板统计。

## 2. MCP 输入（src/mcp.ts 中的 submit_handoff）

- `issues?: [{ problem, repro?: { command, cwd?, expect }, late_reason? }]`：只用来报新问题。
- `rechecks?: [{ id, status: "fixed" | "not_fixed", note? }]`
- `addressed?: [{ id, how, verified? }]`
- `review_comments` 保留，描述改为「旧写法；建议改用 issues」。

编号由 `submitHandoff` 统一分配，规则如下：
- 分配时机是全部校验通过之后，按数组顺序依次编号。
- n 等于本任务已有交接中 `data.issues[].id` 的最大序号加 1。
- 唯一性的范围是任务行（task.id），编号字符串里不带运行号。
- 不给旧数据回填编号。
- 单任务的流水线运行也写成 `T1-B1`。

## 3. 拒绝条件

以下校验全部在 `scopeAndCommit` 之前执行。校验失败时返回 `err` 并列出相关编号，不做 git 提交，不写交接，不确认信件，attempt 保持 `in_progress`，修正后可以直接重新提交。

先定义两个概念：
- **审查阶段**：`stage.on_reject` 有值，或本次传了 `verdict`。
- **待核对集合**：本次 attempt 的 `feedback.blocking` 里所有 `id` 不为 null 的项。

| # | 条件 |
|---|---|
| V1 | 非审查阶段传了非空的 `issues` 或 `rechecks` |
| V2 | 传了非空的 `issues` 或 `rechecks`，或者待核对集合不为空，但没有传 `verdict` |
| V3 | 输入的 issue 带了 `id` 或 `ref` 字段（schema 使用 strict 模式）；或者 `issues` 和 `review_comments` 同时非空，要求二选一 |
| V4 | `repro` 的 `command` 或 `expect` 为空；或者 `cwd` 是绝对路径，或规范化之后跑出了项目根 |
| V5 | 待核对集合为空，却传了非空的 `rechecks` |
| V6 | `rechecks` 没有恰好覆盖待核对集合：漏答、重复编号、未知编号，三类分组列出 |
| V7 | `verdict: reject`，但既没有 `not_fixed`，也没有新问题（新 `issues` 或旧写法 `review_comments` 都算） |
| V8 | `verdict: approve`，但带了新 `issues`，或者存在 `not_fixed` |

以下情况不拒绝，只写进 `scope_notes`，审批卡上会显示：
- 复审时提出的新问题没写 `late_reason`。
- `addressed` 漏写了某个编号，或含有未知编号、重复编号，或者 `verified` 为空。未知编号和重复的那几组不会并入复审信。
- 传了 `addressed`，但当前不是返工阶段。

旧写法这样处理：
- `review_comments` 配合 `reject`：每条转成 `{ problem }`，按同样的规则编号。
- `review_comments` 配合 `approve`：沿用现在的处理，当作观察，不编号。

## 4. 派生和载荷

- **`data.review_comments`**：由桥写入，内容是 `openAfter` 算出的结果。
  - 每条格式为 `T2-B3：描述（复现：命令 @ cwd；期望：…）`。
  - 状态为 `not_fixed` 的问题加前缀 `[未修复] `。
  - 旧面板和 git 提交信息都直接读这个字段，不用改。
- **`decide(reject)`**：
  - 审查方的 verdict 是 reject 时，下一轮的 `feedback.blocking` 等于 `openAfter(attempt.feedback.blocking, h.rechecks, h.issues)`。也就是去掉已修复的，保留未修复的，加上本轮新增的，每项都带 repro。
  - 旧数据里没有编号的项只出现一轮。复审方如果认为它仍然是阻塞问题，可以作为新问题重新提出，获得新编号。
  - 审查方的 verdict 是 approve、但人工点了打回时，blocking 为空，和现在一样。
- **人工批准一份 reject 审查**：按现有推进逻辑走，下游阶段的 feedback 里没有 blocking，所以不要求复核。这相当于豁免，不需要额外的状态。
- **返工信**：
  - `feedback.blocking` 带上编号和 repro。
  - 说明文字写：「提交前逐条运行 blocking[].repro，确认结果符合 expect；在 addressed 里按编号写怎么处理、跑了什么命令、结果是什么」。
  - `input_handoff` 去掉 `review_comments`、`observations`、`issues`、`rechecks`。
- **复审信**（carried）：
  - `feedback.blocking[]` 的每一项并入返工方对应的 `addressed: { how, verified } | null`。
  - `input_handoff` 去掉 `addressed`；上一轮的 observations 也照旧去掉。
  - 说明文字写：「rechecks 必须覆盖 feedback.blocking 里所有带编号的项，否则提交被拒；复审提出的新问题写 late_reason」。
- **`room.handoff()`**（T2 负责）：新增 `issue_summary: { previous_open, fixed, not_fixed, added, late }`，其中 `previous_open` 等于 `rechecks.length`。
  - 复审卡显示：「上一轮 4 项：已修复 3，未修复 1；新增 2」。
  - 首次审查只显示：「新增 N」。

### 关键决策

- 编号和状态存在交接数据里（data.issues、rechecks、addressed），不建新表，不回填旧数据 —— handoff 本来就是按任务追加写入的唯一事实来源，不用迁移，也不会出现两份状态。0.10.1 的旧库只需读兼容，无编号的项读成 id 为 null。
- 复审的必答集合就是本次 attempt 的 feedback.blocking 里带编号的项；下一轮的 blocking 由 openAfter 纯函数算出 —— 人工批准一份 reject 审查后，下游的 blocking 自然为空，不需要另设 waived 状态，也不用扫描历史。校验和 decide 用同一个函数，结果不会出现两种。
- 复审漏答、重复或未知编号一律硬拒绝；addressed 和 late_reason 缺失只写进 scope_notes —— run #7 T2 的根本问题是上一轮哪些修好了没人逐条回答。拒绝时没有任何副作用，错误信息列出缺的编号，代价只是多一次调用。返工方不会被卡住。
- issues 不接受 id 和 ref；issues 与 review_comments 同时非空时拒绝；不做「描述相同就拒绝」 —— 引用旧问题只走 rechecks 这一条路，避免同一个问题占两个编号。文本完全匹配很少真正命中，碰上泛泛的描述反而会误伤。
- rechecks 里保存当轮的问题快照，issues 里由桥写入 added_in_recheck —— 两者记录的都是事实，不会随规则变化而过期。每份交接卡都能独立渲染，面板不用回放历史。
- shared_dir 是 .bridge/shared/<run.id>/<task.id>/，取信时懒创建，失败时带上 shared_dir_error 但不阻断；任务结束后不清理 —— 数字路径能避开 Windows 保留名和大小写冲突。懒创建让升级前就在进行的任务也能拿到目录。保留目录方便复盘，目录在 .bridge/ 里，不会进 git。
- T1、T2、T3 都由 codex 负责，claude 审查；T4 由 deepseek 负责；顺序是 T1→T3→T2→T4 —— 这是用户的要求：需求明确的编码交给 codex，deepseek 只做文档类的轻活。定稿后 T2 的接口已经完全确定，没有设计上的歧义。

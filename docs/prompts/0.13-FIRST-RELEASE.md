## 1. 背景：发布前的代码审查（用户提供，已逐条核实，已修复）

下面三项已在 `f5ea68b` 修复：先由 astra 修复，再在本仓库复核，结果是 typecheck、build 通过，完整 smoke 432 项全部通过，另外补测了 12 种通配符写法，以及中文提交标题和中文文件名。本阶段**不再重做**，只在 T3 的文档和 CHANGELOG 里记录。

| 优先级 | 问题 | 核实结果 |
|---|---|---|
| **P1** | **git 提交失败后，交接仍然成功。** `scopeAndCommit` 把 git 错误写进 `commit_error`，`submitHandoff` 随后照常写入交接、确认任务信、推进阶段。开着自动提交时，如果提交钩子失败，审查方或依赖 `T1@implement` 的下游会收到任务，但拿不到这次改动对应的提交。 | 属实。`CommitResult` 本来就区分 `error` 和 `skipped`（不是仓库、没有改动），但 `scopeAndCommit` 把两者都写进 `commit_error`，后面的流程分不出来。 |
| **P1** | **目录通配符把范围外的文件算进任务。** `globMatch` 把 `**/` 连同目录分隔符一起换成 `.*`，所以 `src/**/index.ts` 能匹配 `src/tools/myindex.ts`。后果有两个：制造本不该有的租约冲突；按范围提交时把别的文件一起提交。 | 属实。实际运行 `globMatch` 和 `globsOverlap`，两者都返回 `true`。 |
| **P2** | **同一路径从共享租约升级为独占时，回执和数据库不一致。** 续租只调用 `setLeaseExpiry`，更新了到期时间，模式没变；回执却照抄这次请求里的 `exclusive: true`。原来是共享租约的话，其他成员之后仍能拿到共享租约。 | 属实。 |

修复后还有两处小问题，放进本阶段：

- **跳过原因以红字显示。** 真正的 git 错误现在不会生成交接，所以交接里的 `commit_error` 只剩跳过原因，例如「未提交：没有文件改动」，以及新加的「未提交：已关闭自动提交」。面板却仍然把它当错误，用红色显示（`bad`/`form-error`）。关闭自动提交的项目，每次交接都会出现一行红字。
- **smoke 里还有一处靠固定 sleep 的计时。** 第 1021–1030 行用固定的 sleep 等桥重启、等 hook 重新挂上（等 4 秒，而 hook 每 2 秒重试一次）。复核那次运行在这里挂过一次，重跑就通过了。它和 0.11 修过的 K 段是同一类问题。

另外，用户问「刚更新过，现在运行的是哪个版本」时，目前答不上来：`/api/state` 不返回守护进程的版本和提交号，`doctor` 只显示「桥正在运行：项目 …」。

## 2. 目标

1. **发布门槛收尾**：
   - 三个修复已完成，保留 `handoff-lease-smoke.ts` 作为回归测试；
   - 跳过原因改成中性的「提交说明」显示；
   - smoke 里所有「重启守护进程后固定 sleep」的地方改成轮询等待，直到条件成立或超时。
2. **安装版和运行版一目了然**：
   - 守护进程在 `/api/state` 里返回启动时的版本、提交号、启动时间、项目和端口；
   - `doctor` 同时列出全局安装的 CLI 和正在运行的守护进程，两者不一致时明确提示重启；
   - 面板上也能看到当前运行的版本。
3. **发布与更新标准化**：
   - 写明发布流程：改版本号、写 CHANGELOG、`npm pack`、上传到 GitHub Release；
   - `ai-bridge update` 默认安装最新的 Release；
   - 新用户可以直接从 Release 的安装包装好。
4. **面向新用户的文档**：
   - 中英双语 README，包含真实截图；
   - CHANGELOG 从 0.8 记到 0.13；
   - 首次安装、升级、卸载、常见问题，以及安全说明：只监听 127.0.0.1，会修改哪些客户端配置文件，备份放在哪里。
5. **用真实的安装路径验收**：由用户在一个干净的 Windows 环境里，用候选安装包走完「首次安装 → 启动 → 成员加入 → 一次交接 → 一次人工审批」，再从 0.12 升级一次。README 里的命令和截图都以这次实际操作为准。

**smoke 的写法沿用 0.12**：
- 每个任务写自己的 `scripts/<主题>-smoke.ts`，最后用一行 import 接入 `scripts/smoke.ts`。接入前先 `reserve_paths`，**改完那一行就立即 `release_paths`**，不要一直占到交接。

## 4. 设计方向

以下是草案。字段名、拒绝条件和命令行参数由会议定稿写死。

### 4.1 已完成的修复（`f5ea68b`，只需记录）

- **提交失败**：真正的 git 错误（钩子失败，或 `status`/`diff`/`commit` 本身失败）会返回错误，并带上 git 输出的前 4000 字。这时不写交接，任务信保持「已取走」，阶段保持 `in_progress`，并记录 `commit_failed` 的日志和事件。跳过的情况（范围内没有改动、关了自动提交、不是仓库）照常推进。commitPaths 先 add 再 commit，提交失败时文件仍留在暂存区，重试时会重新 add，不影响结果。
- **通配符**：`**/` 换成 `(?:[^/]+/)*`；放在末尾的 `**` 仍是 `.*`。
- **租约**：`renewLease` 用一条 SQL 同时更新模式和到期时间，回执取数据库里实际保存的值。升级为独占时，原有的冲突检查会拦下其他成员的共享租约。
- 所有 git 调用都加了 `LC_ALL=C`，以便按英文报错文字判断「不是 git 仓库」。已确认中文提交标题、正文和中文文件名都不受影响。

### 4.2 提交说明改为中性显示

- 交接对外（`/api/state`、`room.ts`、各面板）增加 `commit_note` 字段，内容是跳过原因，用中性颜色显示，例如灰色的「未提交：没有文件改动」。
- 数据库的 `handoffs.commit_error` 列保留，不改表结构。0.13 之前的旧记录里如果是真正的错误文字（不以「未提交：」开头），仍按错误样式显示。判断规则由会议定稿。
- `submit_handoff` 返回里原有的 `commit_note` 保持不变。
- 主面板（`handoff.js`、`folder.js`）、`/v1`、`/classic` 都要改，各自都能分清「提交说明」和「真正的错误」。

### 4.3 smoke 计时加固

- 新增一个通用的等待函数，例如 `waitFor(read, description, timeoutMs)`，和 `acp-smoke.ts` 里的 `until` 是同一种写法，可以抽成公用的。
- 第 1021–1030 行改成：重启后轮询，直到 `doorbellArmed` 为真，超时再报失败。顺带检查 `smoke.ts` 里其他「重启守护进程后固定 sleep」的地方，一并改掉。
- 这一项只改测试，不改功能代码。

### 4.4 版本核对

- `/api/state` 增加一个字段，比如叫 `daemon`，内容为 `{ version, commit, built_at, started_at, project, port, install_dir }`，取自守护进程启动时读到的 `package.json` 和 `dist/build-info.json`。用 `npm start` 直接从源码运行时，提交号标为 `dev`。
- `doctor` 新增一节，列出：
  - 全局安装的 CLI 的版本和提交号；
  - 正在运行的守护进程的版本、提交号、启动时间、项目和端口；
  - 两者不一致时，提示「停掉 ai-bridge 后重新 ai-bridge start」。
- 面板页脚，或者成员面板里，显示守护进程的版本和提交号。

### 4.5 发布与更新

- `scripts/release.mjs`（名字由会议定）：
  - 检查版本号、`CHANGELOG.md` 里有没有本版本的小节、工作区是否干净；
  - 运行 typecheck、build 和 smoke；
  - `npm pack` 生成安装包；
  - 打印 `gh release create v<版本> <tgz> --notes-file <本版本小节>` 这条命令，但**不执行**。
  - 支持 `--dry-run`。
- `ai-bridge update`：
  - 默认取最新的 GitHub Release，下载里面的安装包后再安装；
  - `--channel main` 保留现在的做法（从 main 构建）；
  - Release 不存在或下载失败时，给出清楚的提示，并保留旧版本；
  - 仍然遵守「全局安装只在最后一步才会被替换」。
- `doctor` 的版本比较：装的是 Release 时，和最新 Release 比较；装的是 main 构建时，和 main 比较（沿用第 21 节的 Compare API 做法）。
- 新用户安装：README 给出一条命令，`npm install -g <Release 安装包的地址>`，然后 `ai-bridge setup`、`ai-bridge init`、`ai-bridge start`。安装包里要带上 `dist/build-info.json`，以确认 `npm pack` 的产物能直接装。

### 4.6 文档与截图

- `README.md`（中文）和 `README.en.md`（英文），开头互相链接，结构一致：
  - 是什么、为什么用；
  - 支持哪些产品，以及已验证的版本；
  - 安装、快速开始：从第一个项目到第一次审批；
  - 截图：主页、会议、交接卡（带编号的阻塞问题）、Office；
  - 更新、卸载；
  - 安全说明：只监听本机；修改哪些配置文件，备份放在哪里；没有遥测；
  - 常见问题：叫不醒、端口被占、版本不一致；
  - 许可证（待定）。
- `CHANGELOG.md`：按版本列出 0.8 到 0.13，每条一两句，内容取自 ARCHITECTURE 第 20 到 26 节。
- 截图放在 `docs/images/`，在 7879 的演示项目里截取，用的是演示数据。PNG 尽量控制在几百 KB 以内。截图由能控制浏览器的成员截，Claude 桌面版有内置浏览器；截不了就在交接里写清楚，留给用户补。

## 6. 验收标准

- `npm run typecheck`、`npm run build`、`npm run smoke` 都通过。各模块至少覆盖：
  1. `handoff-lease-smoke.ts`（`f5ea68b` 的三项修复）照常通过；
  2. 跳过时交接里的 `commit_note` 有值，面板用中性样式显示；以「未提交：」开头的旧记录也按提交说明显示；真正的错误文字仍按错误样式显示；
  3. 桥重启那段用例改成轮询后，连续跑 3 次完整 smoke 都通过；
  4. `/api/state.daemon` 的字段齐全；`doctor` 在全局版本和运行版本不一致时给出提示（用假的安装目录或守护进程测试）；
  5. `release.mjs --dry-run`：CHANGELOG 缺本版本小节或工作区不干净时退出码非 0；正常情况下打印 `gh release create` 命令，不执行；
  6. `update` 的 Release 通道：用本地的假 Release（或者桩掉的 `gh`/HTTP）验证下载、安装和失败时保留旧版本，不访问真实的网络和 GitHub。
- 在 7879 的临时项目里，用 `npm pack` 生成的安装包装到一个隔离的前缀目录（`npm i -g --prefix <临时目录>`），走一遍 setup（隔离 HOME）、init、start、join、一次交接、一次审批。截图就从这次操作里截。
- 文档和代码一致：CLAUDE.md 与 AGENTS.md 同步；`DEFAULT_CONFIG_YAML` 与 `bridge.config.example.yaml` 同步；README 的中英文内容一致。

## 7. 运行结束后由用户做的步骤（不在任务里）

1. 选择开源许可证，补进 `package.json` 和 README。
2. 在干净的 Windows 环境（例如 Windows Sandbox）里，用候选安装包走完首次安装到审批的整个流程；在自己的机器上从 0.12 升级，确认原来项目的历史能正常读取，已经移除的客户端配置没有被加回来。
3. 跑 `scripts/release.mjs`，确认它打印的命令没问题后，自己执行 `gh release create`，附上同一份验收过的安装包和 CHANGELOG。

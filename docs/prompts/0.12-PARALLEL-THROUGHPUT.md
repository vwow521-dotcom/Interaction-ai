# 阶段：0.12，两个主力同时开工

版本 0.12.0。目标是让 codex 和 claude 同时写代码、交叉审查，缩短一次运行的总耗时，并消除长命令期间的误报。

- `CLAUDE.md` 的 Runs, tasks, attempts、File leases、Meetings 三节；`docs/ARCHITECTURE-v2.md` 的第 19 节（后续设计草案）和第 25 节（0.11 审查效率）。
- `src/engine/scheduler.ts`：`schedule`（第 270 行附近，依赖检查）、`deliver`（每个成员一次只做一个任务）、`turnPayload` 里的 `dependencies`。
- `src/engine/meetings.ts`：`validatePlan`、定稿轮的 `taskSpec` 和 `guide.final`。
- `src/engine/postman.ts`：`sweep` 中 `ack_overdue` 的豁免条件（第 332 行附近）。
- `src/engine/presence.ts`、`src/engine/workspace.ts` 里的 `reportProgress`、`src/engine/activity.ts`。
- `src/mcp.ts` 里的 `report_progress` 和定稿任务的 `planned` 模式。
- `scripts/smoke.ts` 第 23–26 行：smoke 已经拆成多个模块，例如 `member-notes-smoke.ts`。

## 1. 背景：运行 #8 的时间线

0.11 的 4 个任务都一次就通过了审查，但整个运行是严格串行的，共用了 84 分钟：

| 时间 | codex | claude |
|---|---|---|
| 14:03–14:17 | T1 实现 | 空闲 |
| 14:17–14:24 | 空闲 | T1 审查 |
| 14:25–14:42 | T3 实现 | 空闲 |
| 14:42–14:49 | 空闲 | T3 审查 |
| 14:50–15:01 | T2 实现 | 空闲 |
| 15:01–15:21 | 空闲 | T2 审查 |
| 15:22–15:27 | 空闲 | 等 deepseek 写 T4，然后审查 |

原因有三层：

1. **规划。** 0.11 的阶段文档写了「需求明确的编码优先交给 codex」，主持人照做，把 T1、T3、T2 全排给了 codex。T2 只改面板，和 T3 的文件范围不重叠，本来可以由 claude 同时做。这是规划文档的问题，0.12 的文档改正它。桥本身也没有在定稿时提示「这份计划几乎全是串行」。
2. **依赖粒度。** `depends_on: ["T1"]` 要等 T1 审查通过并经人批准才算满足。下游任务如果只需要上游的接口，可以在上游实现交接后就开工，不必再等一轮审查。第 19 节的「审查阶段的独立依赖」草案说的就是这类阶段级依赖。
3. **误报。** 成员跑 4–5 分钟的完整 smoke 时，十分钟内不会调用桥的工具。`sweep` 因此报 `ack_overdue` 并给用户发通知：运行 #8 里 codex 的 T3 报了一次，claude 的 T2 审查也报了一次，其实两边都在正常工作。

## 2. 目标

1. **阶段级依赖。** `depends_on` 可以写成 `T1@implement`，意思是 T1 的实现交接一出现，就可以开工。上游返工以后，正在进行的下游任务会收到通知。
2. **审查优先投递。** 一个成员同时有多个待领取的阶段时，先投递审查。审查耗时短，而且会阻塞别人。
3. **长命令心跳。** `report_progress` 可以带上预计忙碌的时长，期间不报确认超时，Office 上显示「正在执行长命令」。
4. **定稿时预览并行度。** 定稿提交后，桥用纯函数推算任务分成几波、每个成员排了哪些任务，给出不拦截的提示，例如「claude 只负责审查」「整个计划是一条串行链」。审批卡上能看到这份预览。
5. **文档和版本 0.12.0。**

## 3. 禁区

和以前的阶段一样：

- 不运行 `reinstall`、`update`、`setup`；
- 不停止或重启 7878；
- 不读写本仓库的 `.bridge/`；
- 预览用 7879 端口加一个临时 git 仓库。

**smoke 的写法**：每个任务把自己的用例写成单独的模块 `scripts/<主题>-smoke.ts`，只在最后用一行 import 接入 `scripts/smoke.ts`。`scripts/smoke.ts` 不写进任何任务的 `paths`。改这一行之前先 `reserve_paths(["scripts/smoke.ts"])`，改完就 `release_paths`。这样两个并行任务不会在 smoke 上冲突，也顺便实测了临时租约。

## 4. 设计方向

以下是草案。字段名、拒绝条件和提示文字由会议定稿写死。

### 4.1 阶段级依赖（`T1@implement`）

- `depends_on` 的每一项是 `Tn`（不变：上游任务已完成）或 `Tn@<stage_id>`。后者的意思是上游这个阶段最近一次的尝试已经有交接，状态为 done、awaiting_approval 或 approved 均可。
- `validatePlan` 增加校验：
  - `stage_id` 必须是上游任务实际会有的阶段。定稿时按 `task_template` 和上游有没有审查人推出来，比如上游没有审查人，`@review` 就不合法；
  - 成环检查把 `Tn@x` 当成对 `Tn` 的依赖，宁可保守；
  - 带阶段依赖的两个任务会同时进行，所以它们的 `paths` 不能重叠。重叠时拒绝，并说明原因。
- 下游任务信的 `dependencies[]` 每项增加 `based_on: { stage, commit }`，记下开工时依据的那份上游交接。下游交接时，桥把 `based_on` 存进交接数据。
- **上游变化通知。** 下游已经开工以后，上游对应阶段又有新交接（返工后重新提交），或者上游任务被取消，桥给下游负责人发一封不需要确认的通知信。信里写上游的任务号、阶段、新提交、摘要，以及「改动是否影响你，自己判断；需要跟进就改，不需要就继续」。不打断、不作废下游任务。下游的审查信也带上这些变化。
- 上游之后的审查打回不撤销下游已经满足的依赖。人可以在面板上停止下游任务，这一阶段不需要新的界面。

### 4.2 审查优先投递

- `deliver(agent)` 在多个 `ready` 的尝试里挑选时，先挑审查阶段（`on_reject` 有值的阶段），同类再按最早排。
- 不抢占：成员手上已经有进行中的阶段时，仍然等它交接后再投递。

### 4.3 长命令心跳

- `report_progress(agent_id, text, busy_minutes?)`，其中 `busy_minutes` 是 1 到 60 的整数。
  - 桥在内存里记下 `busyUntil`。到期之前，这个成员进行中的任务信不报 `ack_overdue`。
  - `submit_handoff` 或下一次 `report_progress` 会清除或覆盖它。
- `agents[].activity` 和成员详情显示「执行长命令，预计 hh:mm 前」。
- 这条用法写进 `report_progress` 的工具描述和 `join` 的工作守则，例如：「预计超过 5 分钟不调用桥工具时（比如跑完整 smoke），先 report_progress 并带上 busy_minutes」。不改任务信的说明文字。
- 误报的条件不变：超过 `busyUntil` 和 `ack_timeout_seconds` 两者中较晚的那个，仍然没有动静，照常报。

### 4.4 定稿时预览并行度

- 新建纯函数模块，例如 `src/engine/plan-preview.ts`。输入任务清单（含 `@stage` 依赖）和阶段模板，输出：
  - 分波：每个任务的阶段按 1 个单位计时，每个成员一次只做一个阶段；
  - 每个成员的实现数和审查数；
  - 提示列表，规则由会议定，至少包括：
    - 只有一位成员在写代码，而另一位只做审查；
    - 整个计划是一条串行链；
    - 同一负责人名下有多个任务，它们之间没有依赖却只能串行。
- `submit_meeting_turn` 的定稿返回带上 `preview`。提示不拦截提交。面板的定稿卡显示分波和提示。
- 定稿轮的说明文字（`guide.final` 和 `taskSpec`）补充两点：`Tn@stage` 的写法，以及「主力成员尽量同时各做一个实现任务，并交叉审查」。`mcp.ts` 里 `planned.depends_on` 的描述也同步更新。

## 6. 验收标准

- `npm run typecheck`、`npm run build`、`npm run smoke` 都通过。各模块至少覆盖：
  1. `T2` 依赖 `T1@implement` 时：T1 一交接 T2 就开工；T2 的任务信带上 `based_on`；T2 的交接数据记下 `based_on`；
  2. T1 返工后重新交接，进行中的 T2 负责人收到通知信，T2 照常进行；T2 的审查信列出这次变化；
  3. `validatePlan` 拒绝以下情况，并逐条说明原因：不存在的阶段、上游没有审查人却写了 `@review`、成环、带阶段依赖的两个任务 `paths` 重叠；
  4. 一个成员同时有待领取的实现阶段和审查阶段时，先收到审查；
  5. 用 `busy_minutes` 汇报后，超过 `ack_timeout_seconds` 也不报 `ack_overdue`；过了 `busyUntil` 仍没动静时照常报；交接后清除；
  6. 预览对「一人包办全部编码」「整条串行链」「两人并行」三种计划给出不同的提示和分波；提示不拦截定稿；
  7. 不带 `@` 的旧计划和 0.11 的数据库照常运行。
- 在 7879 的临时项目里走一遍「定稿（含 `@implement`）→ 两个任务同时进行 → 上游返工通知」，确认面板的定稿卡和 Office 显示正确。
- 文档和代码一致，`DEFAULT_CONFIG_YAML` 和 `bridge.config.example.yaml` 同步。

## 7. 本阶段不做

- **0.13 产品化**：中英双语 README 和截图，用 GitHub Releases 发布、写 CHANGELOG，标准化安装和更新流程。这是接入更多成员的前提。
- **任务描述勘误**（第 19 节）：可以和产品化一起做，或者排在它之后。
- **手机和局域网访问**：先调研局域网暴露带来的 DNS、WebRTC 信息泄露问题，再决定要不要做。
- **抢占式投递**（成员做到一半先去审查别的任务）和**跨运行的长对话提示**。

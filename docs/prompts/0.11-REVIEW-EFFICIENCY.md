# 阶段：0.11，审查效率（结构化阻塞问题、复现命令、共享工作区）

版本 0.11.0。目标是让「实现 → 审查 → 返工 → 复审」少转几圈，每一圈都有据可查。

## 0. 先读

- `CLAUDE.md` 中 Runs, tasks, attempts 一节和 `git.ts` 一节；`docs/ARCHITECTURE-v2.md` 第 19 节（后续设计草案）和第 24 节（信件去重）。
- `src/store.ts`：`HandoffData`、`Feedback`。
- `src/engine/scheduler.ts`：`turnPayload`、`submitHandoff`、`decide`。
- `src/mcp.ts`：`submit_handoff` 的输入定义。
- `panel/js/cards/handoff.js`（主面板的交接卡），以及 `panel.ts`、`panel/v1/room.js`（旧面板，只需保持能显示）。
- `scripts/smoke.ts` 的 B 段（打回与复审）和 D 段（会议产生的任务）。

## 1. 背景：真实数据

下面的数据来自 `.bridge/bridge.db` 里 7 个运行的回放。

- 多数任务一次返工就能通过。最差的是 run #7 的 T2：实现 → 审查共 4 轮，打回 3 次。每轮实现耗时 21、13、8、9 分钟，审查耗时 6、4、3、3 分钟。
- 看 T2 三次打回的理由：
  - 第 1 轮列了 4 个阻塞问题；
  - 第 2 轮说「上轮四项已修复」，又提出 3 个**新**问题；
  - 第 3 轮说「上轮四项已修复」，又提出 1 个**新**问题。
  - 也就是说，复审时问题总在变：每轮都有新发现，上一轮哪些已修好、哪些没修好，只写在一段文字里，桥不知道，面板上也看不出来。
- 审查人已经习惯在阻塞问题里写复现步骤，例如「在 85e4e0a 上连续跑 3 次 npm run smoke，第 1、3 次失败……」。这些步骤混在一段话里，返工方要自己摘出来，复审时也没法逐条打勾。
- T3 的审查人「写了个临时运行脚本」单独跑专项测试。脚本没有固定的存放位置，返工方拿不到。
- 0.10.1 的信件去重已经去掉了重复内容。剩下的低效来自审查往返本身。

## 2. 目标

1. **阻塞问题结构化。** 每个阻塞问题有一个稳定编号，例如 `T2-B3`，可以附复现命令。返工信和复审信按编号引用这些问题。
2. **复审逐条核对。** 复审时，对上一轮的每个阻塞问题回答「已修复」或「未修复」。新提出的阻塞问题由桥自动标为「新增」，并要求说明为什么上一轮没发现。面板上能看到每一轮未修复几项、新增几项。
3. **返工方先自查。** 返工信要求返工方在提交前逐条跑一遍复现命令，并在交接单里按编号说明每项是怎么处理的。
4. **共享工作区。** 每个任务有一个不进 git 的目录，存放临时脚本和样例，实现方和审查方都用同一份。
5. **第一次审查尽量一次列全。** 调整默认审查说明（`DEFAULT_TASK_TEMPLATE`、`bridge.config.example.yaml`、本仓库的 `bridge.config.yaml`）。

## 3. 禁区

和 P1 到 M3 相同：

- 不运行 `reinstall`、`update`、`setup`；
- 不停止或重启 7878；
- 不读写本仓库的 `.bridge/`；
- 预览用 7879 端口加一个临时 git 仓库。

共享工作区功能本身会在运行时写 `<项目>/.bridge/shared/`。开发和测试时只在 7879 的临时项目或 smoke 的临时目录里验证它。

## 4. 设计方向

以下是草案。会议里可以修改，定稿时写进决定。

### 4.1 阻塞问题的数据结构

- `submit_handoff` 新增可选参数 `issues`，每项包含：
  - `problem`：问题描述，必填；
  - `repro`：可选，`{ command, cwd?, expect }`；
  - `ref`：可选，只在复审时用，指上一轮的编号；
  - `late_reason`：可选，只给新增问题用，说明上一轮为什么没发现。
- 旧的 `review_comments: string[]` 继续接受。桥把每一条转成只有 `problem` 的 issue。
- 桥给每个新问题分配编号，格式为 `<任务号>-B<序号>`，在任务内递增，返工多少次也不重号。
  - 编号和状态存在交接数据里，或者单独建一张表，由会议决定。
  - `review_comments` 仍然以字符串形式写进交接数据，旧面板、`/classic`、`/v1` 和 git 提交信息不用改就能显示。
- `Feedback.blocking` 改成「带编号的 issue」，读旧数据库时把字符串兼容成 issue。

### 4.2 复审

- 复审信列出上一轮所有未关闭的问题（编号、描述、复现命令），要求逐条回答。
- 复审方提交时带 `rechecks: [{ id, status: "fixed" | "not_fixed", note? }]`。
  - 漏答了哪个编号，桥就拒绝这次提交，并列出缺的编号。做法和 `validatePlan` 一样。
  - `verdict: reject` 至少要有一个 `not_fixed`，或者至少有一个新问题。
- 新问题没有 `ref`。复审时提出新问题而不写 `late_reason`，桥不拒绝，只在审批卡上标出来。这样做是为了约束审查方式，不卡流程。

### 4.3 返工与自查

- 返工信的 `feedback.blocking` 带编号和复现命令。说明文字里写明：「提交前逐条运行 repro，确认结果符合 expect」。
- 返工方的交接单可以带 `addressed: [{ id, how, verified }]`，其中 `verified` 写已跑过的命令和结果。
  - 缺少某个编号时不拒绝，在 `scope_notes` 里提示一句即可。
  - 复审信把 `addressed` 和对应的 issue 放在一起展示。

### 4.4 面板

- 主面板的交接卡（`panel/js/cards/handoff.js`）按编号显示阻塞问题：描述、复现命令（可复制）、状态（未修复、已修复、新增）。
- 复审卡显示一行统计，例如「上一轮 4 项：已修复 3，未修复 1；新增 2」。
- 旧面板只要能把 `review_comments` 字符串显示出来就算合格。

### 4.5 共享工作区

- 任务开始时，桥创建 `<项目>/.bridge/shared/<run>/<task>/`。`.bridge/.gitignore` 本来就排除整个 `.bridge/`，这个目录不会被提交。
- 任务信带 `shared_dir`，用相对于项目的路径。说明文字提示：临时脚本、样例和复现命令用到的文件都放在这里。
- 任务结束后保留这个目录，不自动删除。这样可以回看。要不要清理、怎么清理，由会议决定。

## 5. 建议拆分（供会议参考）

用户的分工约束：
- 需求明确的编码优先交给 **codex**，它擅长按明确需求交付成熟成果；
- **claude** 负责设计上有歧义的部分和审查；
- **deepseek**、**antigravity** 只做文档和文案类的轻活，见各成员的 `notes`。

| 任务 | 内容 | 负责 / 审查 | 依赖 | 预计 paths |
|---|---|---|---|---|
| T1 | 4.1 到 4.3：issue 编号、`issues`、`rechecks`、`addressed` 的输入校验与存储，返工信和复审信的载荷，兼容旧数据，smoke B 段 | codex / claude | — | `src/store.ts`、`src/mcp.ts`、`src/engine/scheduler.ts`、`scripts/smoke.ts` |
| T2 | 4.4：交接卡与复审统计，旧面板保持能显示 | codex 或 claude / 另一位 | T1 | `panel/**`、`src/panel.ts` |
| T3 | 4.5：共享工作区，以及默认审查说明的修改 | codex / claude | T1（两个任务都会改 `scheduler.ts` 和 smoke） | `src/engine/scheduler.ts`、`src/config.ts`、`bridge.config*.yaml`、`scripts/smoke.ts` |
| T4 | 文档：ARCHITECTURE-v2 第 25 节，USAGE 的审查说明，CLAUDE.md 与 AGENTS.md 同步，版本号改为 0.11.0 | deepseek / claude | T1、T2、T3 | `docs/**`、`CLAUDE.md`、`AGENTS.md`、`package*.json` |

T1 是关键路径，接口一定要在定稿时写死（字段名、编号格式、拒绝条件），codex 才能一次交付。T2 和 T3 都依赖 T1：T2 要等接口定下来，T3 和 T1 改的是同一批文件。T4 的技术细节以代码为准，审查人负责核对文档有没有写错。

## 6. 验收标准

- `npm run typecheck`、`npm run build`、`npm run smoke` 都通过。smoke 至少覆盖：
  1. 审查用 `issues` 打回后，返工信的 `feedback.blocking` 带编号和 `repro`，`input_handoff` 不重复这些内容（第 24 节的去重仍然成立）；
  2. 只传旧的 `review_comments` 时，流程和 0.10.1 一样，issue 编号照常分配；
  3. 复审漏答某个编号时被拒绝，错误里列出缺的编号；全部答完才能提交；
  4. 复审时提出的新问题被标为新增，编号接着往下排，不和上一轮重复；
  5. 返工方的 `addressed` 出现在复审信里；漏写编号时只给出 `scope_notes` 提示；
  6. 任务信带 `shared_dir`，目录存在，提交时不会进 git；
  7. 用 0.10.1 的数据库启动时，旧的 `feedback.blocking` 字符串能正常读出来。
- 在 7879 的临时项目里，用假数据或真实成员手动走一遍「打回 → 返工 → 复审」，确认主面板的交接卡能显示编号、复现命令和统计行。
- 文档与代码一致，`DEFAULT_CONFIG_YAML` 和 `bridge.config.example.yaml` 同步。

## 7. 本阶段不做（排到 0.12）

- **审查阶段的独立依赖**（第 19 节）：要改调度的依赖图和成环校验，改动大。目前也还没出现过「审查要等别的任务实现完」的真实需求，先观察。
- **任务描述勘误**（第 19 节）：需要面板入口和版本记录，与本阶段无关。
- 在检测到同一对话跨多个运行变得很长时，提示用户开新对话。用户现在已经是每次开新对话来干活了。

# AGENTS.md

This file provides guidance to Codex when working with code in this repository. It mirrors CLAUDE.md; keep the two in sync.

## What this is

A local "AI collaboration bridge". One long-running Node daemon exposes an MCP server over Streamable HTTP, plus a web panel. AI agents in different desktop products (Claude desktop's Code tab, and Codex inside the ChatGPT Windows app; later Gemini, Antigravity and DeepSeek) use it to hand work to each other through a role pipeline that has human approval gates. Work travels as **mail**, and a **postman** wakes idle agents with product-specific **doorbells** instead of having them poll.

The design docs are in Chinese. `docs/ARCHITECTURE-v2.md` is the current architecture: the postman, the borrowed designs, and the S1/S2 spike results. `docs/DESIGN.md` covers the original goals and decisions. Read them before changing behaviour. The user communicates in Chinese, and the agent-facing tool text and the panel are in Chinese too. How to use the bridge: `docs/USAGE.md`.

Stage: M2b through M2d shipped the postman, meetings, task DAG, file leases, scoped commits, Codex queue doorbell, and chat. P2 (0.8) adds join shortcuts and doorbell diagnostics. P3 (0.9) adds a workspace, home page, folder pages and a now-playing bar. M3 (0.10) completed ACP background members for Antigravity and DeepSeek Harness; 0.10.1 adds the cancel grace, Windows process ownership and `agents.<id>.notes` (shown to meeting facilitators). 0.11 makes reviews countable: blocking issues get task-scoped IDs (`T2-B3`) with optional repro commands, re-reviews answer every open ID, and each task gets a git-ignored `.bridge/shared/<run>/<task>/`. 0.12 lets both main agents code at once: `Tn@stage` dependencies with upstream notices, review-first delivery, serialized handoff commits, `report_progress(busy_minutes)` and a parallelism preview on the final plan (architecture §26). 0.13 is the first public release: it records the `f5ea68b` fixes (a failed commit no longer becomes a handoff, `**/` stays inside directory names, lease mode upgrades are stored), shows skip reasons as a neutral `commit_note`, reports the running daemon's version, installs from GitHub Releases by default and adds `scripts/release.mjs`, a bilingual README and CHANGELOG (architecture §27). Clipboard members are deferred. Treat `src/m0/` and `spikes/` as records. Don't extend them.

## Commands

```
npm start -- --project <dir> [--port 7878]   # dev: run the daemon from src via tsx (MCP /mcp, panel /, JSON API /api/*)
npm run smoke       # end-to-end regression: own daemon on port 7891 (SMOKE_PORT=<port> when two agents run it at once), temp git repos, fake Claude/Codex doorbells and ACP agents
npm run typecheck
npm run build       # tsc -p tsconfig.build.json → dist/ (src/m0 excluded)
npm run reinstall   # npm pack into release/ → npm i -g → ai-bridge setup --refresh → ai-bridge doctor (local tree)
ai-bridge update    # default --channel release: latest GitHub Release asset → check name/version/channel/commit inside the tgz → npm i -g → setup --refresh → doctor
ai-bridge update --channel main [--ref <ref>]   # fetch GitHub main into a temp dir → npm ci → npm pack → npm i -g → setup --refresh → doctor (never `npm i -g github:…`: npm runs the clone's install in global mode, prepare fails, and the old install is already gone)
node scripts/release.mjs [--dry-run]   # preflight (semver, lock versions, CHANGELOG section, clean tree) → typecheck/build/smoke → pack with BRIDGE_BUILD_CHANNEL=release → check the tgz → print (never run) gh release create
npm run cli -- <cmd> [--dry-run]   # run the CLI from this tree (setup/uninstall/init/start/doctor)
```

**The user's Claude and Codex point at the globally installed copy** (`%APPDATA%\npm\node_modules\ai-bridge`), not at this tree. After changing `bin/` or `src/`, run `npm run reinstall` so the clients pick it up; once released, `ai-bridge update` installs the latest GitHub Release (`--channel main` builds from main). `prepare` builds and writes `dist/build-info.json` (`channel` from `BRIDGE_BUILD_CHANNEL`: release, main or dev by default; commit; dirty), which `doctor` compares with the latest Release (release) or GitHub main (main, and old builds without a channel). Never create a Release, push a tag or publish to npm: the user does that after acceptance. `setup --refresh` (used by both) only touches bridge entries that already exist: the user removed Codex's bridge entry on purpose, so never re-add a client they removed. `npm run cli -- setup` would point the clients at this dev tree instead. Testing `setup`/`uninstall` against copied config files is not isolated: they also clean `.codex/hooks.json` in the real project folders listed in the config. Use `--dry-run`.

Extend the smoke whenever you change engine, proxy or hook behaviour. New cases go in their own `scripts/<topic>-smoke.ts` module, wired into `scripts/smoke.ts` with one dynamic-import line. Wait for conditions with `waitFor` from `scripts/smoke-wait.ts` instead of fixed sleeps after a restart. The smoke prints its fixture and progress-log paths first; the progress log (outside the fixture repo) and the unexpected-daemon-exit report locate a native crash (0xC0000409, see architecture §27.5). Parallel tasks keep `scripts/smoke.ts` out of their `paths`: `reserve_paths` it, add the line, declare it in `files_changed`, submit, then `release_paths`.

When using the bridge to change its own code, preview with a temporary Git project on 7879 and let the current bridge carry the handoff. Installation is a separate step.

## Architecture

- `engine.ts` assembles the postman, presence, scheduler, meetings, leases, and project context/panel state under `src/engine/`.
- **Mail is the only way work reaches an agent.** `Postman.sendMail` → `mail` table (one row per recipient, `id` primary key = dedupe) → `kick(agent)` wakes a `wait_for_mail` poller and/or rings an open doorbell. Status flow: `queued → rung → fetched → acked`, plus `stuck` (gave up after `mail.max_rings`; the human is told to wake the agent) and `void` (a task that was stopped or replaced). `sweep()` runs every 5 s, re-rings mail that is rung but not fetched, and flags overdue acks. Rung mail waits while the recipient's connected session is working on a bridge task or meeting turn.
- **Runs, tasks, attempts:** a run is one goal made of **tasks** (a DAG: `depends_on`, `paths`; `tasks` table, status `pending → active → done|cancelled`). Each task runs its own stage chain stored on the task row: a pipeline run ("开始") is one task `T1` whose stages are `pipeline`; a meeting-planned task uses `task_template` with `owner`/`reviewer` filled in (reviewer stages are dropped when a task has none). `depends_on` entries are `T1` (upstream task done) or `T1@<stage>` (that stage's latest attempt has a qualifying handoff: done/awaiting_approval/approved, an awaiting review only with `verdict: approve`, and no later human rejection back to or before that stage; `stage-deps.ts` parses and checks them). `schedule(run)` runs after every handoff and gate decision: it starts every pending task whose dependencies are met and whose `paths` don't collide with someone else's lease, then delivers to every agent with a ready stage, and finishes the run when no task is left. A task started on a stage dependency stores its baseline in `tasks.dep_basis` (`{ dep, stage, handoff_id, commit }`); task mails carry it as `dependencies[].based_on` plus `upstream_state` (current/reworking/superseded/cancelled) and `upstream_changes`, and its handoffs record `data.based_on`. Active downstream tasks get advisory `system` mails (`upstream:<run>:<task>:<dep>:<rework|change|cancel>:<event>:<to>`) when the human confirms an upstream rejection that reaches back to the referenced stage (`rejectionAffectsStage`) or that very stage hands off again; nothing is voided, and the baseline never moves (`Tn@stage` gates the whole downstream task, not just its review). Review-first delivery applies to old plans too. Each stage handed to an agent is an **attempt** (`ready → in_progress → (awaiting_approval → approved|rejected) | done`). An agent works on one task at a time: `deliver(agent)` mails a ready attempt only when it has nothing in progress and no task mail out, reviews (`on_reject` set) first, then the oldest; no preemption. `fetch_inbox` turns a task mail into the turn payload and moves the attempt to `in_progress`. `submit_handoff` commits (the change scan, commit and SHA read are serialized across agents on `Scheduler.gitQueue`), acks the task mail and advances that task. The run is `awaiting_approval` only while every live attempt waits at a gate. A rejection creates a new attempt of `on_reject` with structured `feedback` (`Feedback` in store.ts: user_requirements / blocking / observations); when that rework attempt finishes, its feedback is carried (`kind: "carried"`) into the next stage. Review handoffs may carry `issues` (new blocking problems, numbered `<task.key>-B<n>` after validation) and every re-review must answer each numbered open issue with `rechecks` (`fixed`/`not_fixed`); rework handoffs carry `addressed`. Missing, duplicate, unknown or contradictory entries are refused before the commit, so a failed submission has no side effects. The open set behind `decide(reject)` is recomputed by `openAfter`; approving a reject review leaves the next stage's blocking empty (implicit waiver), and old string `blocking` is read as `{ id: null, problem }`. The payload never repeats itself: a rework's `input_handoff` drops the `review_comments`/`observations`/`issues`/`rechecks` already in `feedback`, a carried review merges each `addressed` into its blocking issue and drops `addressed` from `input_handoff`, and instructions point at fields (`task.paths`, `meeting_minutes`, the stage's own review rule) instead of copying them. Every task mail also carries `shared_dir` (`.bridge/shared/<run>/<task>/`, created on first fetch, git-ignored, kept after the task). Reviews with no file changes still commit (`--allow-empty`, `git.commit_reviews`). `ask_human` doesn't block; the answer arrives as an `answer` mail. Only one open run or meeting exists at a time. Pre-M2c databases get one `T1` task per run on startup (`migrateLegacyRuns`).
- **Meetings** (`meetings`, `meeting_turns`): round 1 is proposals from every participant, then the human opens more critique rounds or asks the facilitator for the final plan (`meetingNext`; allowed before everyone has spoken, the rest of that round's mail is voided). Every round is a `meeting` mail with id `meeting-<id>-<round>-<agent>`; `fetch_inbox` builds the payload (previous round in full except the recipient's own turn, which is a `yours: true` summary unless the agent bound or joined after writing it; one sentence per earlier speaker; the human's note, and any registered minutes path) at fetch time and voids mail for a round that is over. `submit_meeting_turn` acks it; the final turn must carry a valid task list (`validatePlan`: ids, owners, dependency format, unknown or duplicate upstreams, stages the upstream's template really has, cycles projected onto tasks, and non-empty, non-overlapping `paths` on both sides of a stage dependency). The final turn's reply and `meeting_turns.preview` hold a `previewPlan` estimate (`plan-preview.ts`: waves, per-member work/review counts, advisory hints `single_coder`, `serial_chain`, `owner_queue`, `path_serialized`) shown on the approval card and in history. Approving writes the minutes to `meetings.dir` (default `doc/meetings/<date>-<topic>.md`), commits only that file, and creates the run with its tasks.
- **Chat** (`chat.ts`, `chat_messages`): a message is stored once; each @mentioned agent gets a `chat` mail (`chat-<msg>-<agent>`, no ack) whose status is the receipt (fetched = read). Mentions are explicit `mentions` plus `@name` in the text (longest known-name prefix match, so `@claude你好` works; `@all`). Human messages must mention someone; an agent's `say` without mentions is for the human only, replying to another agent's message reaches its author, and `wake: false` wakes nobody. After `chat.max_agent_turns` agent messages since the last human message, agents' mentions stop waking anyone. The chat mail payload carries the reply target and the previous `chat.history` messages. The panel's per-agent message box (`POST /api/mail`) is a chat message to that agent; `POST /api/chat` is the room.
- **File leases** (`leases` table): an active task holds an exclusive lease on each of its `paths` (no expiry, released when the task ends or the run stops). Agents add more with `reserve_paths` (TTL, renewed by calling again; expired leases stop counting and show yellow) and drop them with `release_paths`. A conflicting request is refused, returns the holder, and mails the holder. `globsOverlap` is exact for literal paths and conservative (literal-prefix check) when both sides have wildcards; a trailing `/` means the whole directory.
- **Doorbells** (`src/doorbells/`): the only code that knows how a product is woken. The engine never branches on a product; it asks the `Doorbells` registry. Each agent has an ordered **chain** (config `agents.<id>.doorbell`: a list, a single kind, or `auto` = the default in `src/products/`: `codex` → `codex-queue, codex-hook, poll`; `claude-code` → `claude-socket, poll`; unknown product → whatever registers). `poll` always ends a chain. `kick(agent)` wakes a blocked `wait_for_mail`, then rings the first doorbell that is `available()` now. A failed ring (`ringFailed`) requeues the mail and falls through to the next one. After a successful ring of a `verify` doorbell, `checkWake` waits `BRIDGE_WAKE_GRACE_SECONDS` (default 30): any tool call from the agent, or the agent already working on a bridge task, counts as awake. Otherwise it tries the next doorbell, and when none is left, `alertUnanswered` shows "叫不醒" on the panel and sends a toast. `join`'s waiting instructions come from the chain's first `possible()` doorbell. Adding a product takes a driver and a product profile.
  - `claude-socket` (`parked.ts`): `bin/bridge-mcp.mjs`, the stdio MCP proxy, forwards every call to the daemon and sends MCP `DELETE` on stdin EOF to release its session's bindings. In Claude it injects `_doorbell: "claude-socket"` into `join`, long-polls `GET /api/doorbell/wait`, and writes `{"type":"auth"}` + `{"type":"user"}` NDJSON frames to the undocumented `CLAUDE_CODE_MESSAGING_SOCKET` Windows named pipe when rung. Failures are reported to `/api/doorbell/result`.
  - `codex-queue` (`codex-queue.ts`): the bridge runs `codex queue --thread <id> --message <wake text>`. The Codex desktop app drains `~/.codex/queue_1.sqlite` itself: an idle conversation starts a real new turn in ~6 s (`turn_trigger: "queue"`), a busy one picks it up when its turn ends. The CLI is `BRIDGE_CODEX_BIN` (a `.js/.mjs` runs under node), else the newest `~/.codex/packages/app-server-daemon/releases/*/bin/codex.exe`, else `codex.exe` on PATH. It skips queuing when Codex's queue already holds an item for the thread, or while a `codex queue` call for it is still running (run #6: two mails seconds apart caused an empty turn). A failure takes it out of the chain for 10 minutes. The thread id is the agent's `codex-thread` endpoint; it is ignored when it was registered before the agent's current binding (a new conversation that hasn't ended a turn yet) or, if the agent hasn't joined since the daemon started, before the daemon started (run #5: a restart woke the user's old conversation). Such mail waits for the next Stop hook registration.
  - `codex-hook` (`parked.ts`, `bin/codex-stop-hook.mjs`): the Codex Stop hook. Threads without a completed `bridge.join` `McpToolCall` in the transcript get `{}` at once. A joined thread registers its `session_id` (`POST /api/agents/:id/endpoint`, kind `codex-thread`; the old `/api/codex/thread` still works). The answer `park:false` (codex-queue can reach the agent) makes it return `{}` so the turn ends; otherwise it parks on `/api/doorbell/wait` and answers a ring with `{"decision":"block","reason":…}`. Codex drops many of those blocks (§14 of the architecture doc), which is why codex-queue comes first. It logs stdin, parking time, mail IDs and stdout to `<tmp>/ai-bridge/codex-stop-hook.jsonl`, heartbeats after a quiet park window, and rides out a bridge restart for `BRIDGE_DOWN_GRACE_SECONDS` (default 90). While it is parked, Codex holds the user's typing and queued messages until the hook returns.
  - The registry records wake outcomes by agent and driver. Verified doorbells cool down after repeated unconfirmed wakes, and a queue command failure starts the same cooldown immediately. Format drift adds diagnostics to the member panel and inbox. Section 21 of `docs/ARCHITECTURE-v2.md` covers the read-only probes and version checks.
  - `acp` (`acp.ts`): configured background members use one lazily spawned process and one ACP session per project. The session mounts MCP over stdio for Antigravity (`bridge_acp`, to avoid an interactive MCP with the same name) or HTTP for DeepSeek Harness. The driver persists `acp-session` endpoints, resumes before loading or creating, and starts a fresh HTTP session after a daemon restart. A blocked or recent interactive poll gets priority. The daemon scopes managed MCP sessions to their member and applies takeover to managed joins. It cancels turns when their mail is voided with a fixed 30 s grace (`BRIDGE_ACP_CANCEL_GRACE_SECONDS`); a timeout ends the process tree without counting a failure, and the cancelled task keeps its leases until the turn ends, so overlapping or path-less tasks wait. Crashed workers retry after 30 s and 2 min and stop on the third failure. On Windows each agent runs under a detached supervisor (`bin/acp-supervisor.mjs`) that holds its stdio and ends the agent's whole tree when the daemon dies; `src/doorbells/acp-process.ts` records exact identities in `.bridge/acp-hosts.json` before any ACP traffic, and the startup sweep ends only re-verified orphans. Member details show live output and permissions. `doctor --probe` sends only ACP `initialize`. See architecture §23.
  - The desktop app's app-server control socket can't wake a desktop thread: it belongs to a separate managed App Server and answers `thread not found` (tested 2026-11-19).
- **Durable vs in-memory:** runs, tasks, attempts, handoffs, leases, meetings, mail, notes, questions, events and agent endpoints (`agent_endpoints`, e.g. Codex conversation ids) are in `<project>/.bridge/bridge.db` (`store.ts`, `node:sqlite`). Presence, identity bindings, parked doorbell waiters, wake alerts and blocked waits are in memory. After a restart agents re-`join`, and `resendLiveTask` re-mails a live task.
- **Identity binding:** each agent_id is bound to one MCP session (`bindingError`). A second session can only take it with `join(takeover=true)`, or after the human presses 释放 on the panel (`release`) or the agent calls `leave`. A closed session leaves an identity eligible for the next MCP tool call to rebind, with an explanation in its response. The Claude proxy caches its last successful join by messaging socket hash and replays it with `takeover` after the proxy or daemon restarts. Claude desktop shuts idle conversations down and reopens them with a new messaging socket (run #6), so there is no cache to replay: the proxy sends `x-bridge-doorbell: claude-socket` on every MCP request (kept per session in `presence.sessionDoorbell`), an identity recovered on any tool call gets the claude-socket doorbell back (the response says `doorbell` and the right waiting instructions), and the proxy, seeing `identity_recovered`, joins once in the background to cache a resume key for the new socket and re-arms its long-poll. Queued mail that no doorbell can deliver alerts the human after `BRIDGE_UNREACHABLE_ALERT_SECONDS` (default 15) and stays queued. A per-project resume key is revoked by release, leave or an explicit takeover.
- `daemon.ts` serves HTTP, MCP, the JSON API and SSE `/api/stream`. `/api/state.daemon` is a startup snapshot `{ version, commit, dirty, channel, built_at, started_at, project, port, install_dir }` (`commit`/`channel` are `dev` when run from `src` via tsx); the panel's top bar shows it (`#daemon-version`), and `doctor`'s 运行中的桥 section compares it with the CLI. The panel at `/` uses native ES modules for Home, Folders, Office, Chat and the action sidebar. `engine/folders.ts` projects the workspace through `/api/folders`, `/api/folders/:id`, `folders_head` and `now_playing`. A meeting and its resulting run share a folder. `engine/room.ts` derives `inbox`, and `engine/activity.ts` derives `agents[].activity`. SSE refreshes the state and the open folder. Shared fields use `data-keep` for in-tab drafts. Mutations use the existing POST routes. The previous meeting room is at `/v1` (`panel/v1/`), and the classic panel is at `/classic` (`panel.ts`). `notify.ts` shows Windows toasts through PowerShell/WinRT. Set `BRIDGE_NOTIFY=0` to disable them.
- The mail sweep exempts live `in_progress` tasks with tool activity in the configured acknowledgement window, and the task mail of an attempt whose agent called `report_progress` with `busy_minutes` (1–60, in memory on `presence.busy`, tied to that attempt and binding; cleared by a plain report, takeover, release or session close, void once the attempt leaves `in_progress`; `agents[].activity.busy_until` drives the Office line; `BRIDGE_BUSY_MINUTE_MS` shortens it for the smoke). Doorbells with `waitsForTurn` use the extra `BRIDGE_WAKE_TURN_EXTRA_SECONDS` grace after recent tool activity. New minutes use `<date>-m<id>-<topic>.md` (a dot between digits stays in the short title). Listener startup checks the port before opening the project store. `checkWake` confirms a wake by the agent's tool-call count (`presence.callSeq`) rising after the ring, not by timestamps. Meeting events carry `events.meeting_id` (written by `ctx.event`, backfilled once from the event templates on older databases), and folder queries use it with per-run and per-meeting indexes.
- `git.ts`: a task with `paths` or leases, or with other active tasks, commits declared changes and changes in its own scope, excluding other tasks' leases. Reviews commit only declared changes and can record a verdict via an empty commit (`git.commit_reviews`). Scoped submissions use `commitPaths` (`git add -A -- <pathspecs>` + `git commit --only`, pathspecs `:(top,literal)…`). A lone non-review task without paths or leases retains `commitAll`. `changedFiles` is compared with `files_changed`, the task's `paths` and other stages' `owns`; the task's starting dirty paths and other active tasks' leases classify files left uncommitted. These and other mismatches become `scope_notes` (shown on the approval card, not blocking). A real git failure in a handoff returns an error and writes no handoff (the stage stays `in_progress`); a skip is stored in `handoffs.commit_error` as 「未提交：…」, and `store.parseHandoff` splits that column by the exact prefix into `commit_note` (neutral in every panel) and `commit_error` (only pre-0.13 real errors). `.bridge/` writes its own `.gitignore`.
- `cli.ts` provides `ai-bridge` through `bin/ai-bridge.mjs` and `dist/cli.js`. `setup` configures the stdio bridge in `~/.claude.json` and `~/.codex/config.toml`, installs managed `bridge` skills and a user-level `~/.codex/hooks.json` Stop hook, and cleans up older project hooks. It backs up owned files before writing or removing them. `setup --refresh` refreshes an owned skill only if its client still has a bridge entry. `uninstall` removes managed files. `doctor` checks bridge paths, skills, hook trust and product versions. `doctor --probe` inspects doorbell formats and proxy reports without queueing a wake.
- `config.ts`: `<project>/bridge.config.yaml`, validated with zod (`pipeline`, `task_template`, `meetings`, `leases`, …). `DEFAULT_CONFIG_YAML` must stay in sync with `bridge.config.example.yaml`.
- `AGENTS.md` mirrors this file for Codex; update both together.
